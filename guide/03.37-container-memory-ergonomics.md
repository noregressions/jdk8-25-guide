| **Detect** | Run `-XX:+PrintFlagsFinal` *inside the actual target container* and compare effective values between images |

```
JDK 8 (8u502), 512MB cgroup limit:   MaxHeapSize := 134217728   (128MB — 25% of the limit)
JDK 25,        512MB cgroup limit:   MaxHeapSize  = 134217728   (identical)
```

The early-container-era horror story is real: a JVM in a 512MB pod sizing its heap from the host's 64GB, then being OOMKilled mid-request with no Java-side error at all. What this chapter establishes — by measurement — is *which* JDK 8 deployments that story still applies to, because the answer is narrower than the folklore.

---

## What happened

JDK 10 taught HotSpot's ergonomics to read cgroup limits — heap percentages compute against the *container's* memory, not the host's — and the fix was backported to JDK 8u191, released in 2018. The verified runs below show a current 8u patch and JDK 25 behaving **identically** under a real cgroup limit: both settle on 25% of the constrained memory. For any team running a reasonably patched JDK 8 image, container ergonomics is *not* a migration delta at all.

The exposure is therefore concentrated precisely where this level keeps finding it: **frozen images**. A pre-2018 JDK 8 base image — pinned years ago, never rebuilt — still sizes off host RAM, and for that estate the migration doesn't introduce a subtle change, it introduces a large *correction*: pods whose heaps silently shrink from "25% of the host" to "25% of the limit", which can surface as new OOMEs in Java (the heap is now genuinely smaller) even as the OOMKills stop.

One honesty note, in this guide's tradition: the *broken* pre-8u191 behaviour could not be demonstrated in this project's sandbox — the Adoptium archive no longer serves pre-2018 builds, so the verification confirms the fixed world on both sides rather than reproducing the broken one. The claim about pre-8u191 images rests on the documented history, not on a fresh run; if you still *have* such an image, the test script will show you the contrast directly.

---

## Detect

Inside the real container image, with the real limits applied:

```bash
docker run --memory=512m your-image java -XX:+PrintFlagsFinal -version | grep -E "MaxHeapSize|MaxRAMPercentage"
```

Compare between your current JDK 8 image and the target JDK 25 image. And check the image's actual patch level (`java -version`) — the date of that build is this category's entire risk assessment.

---

## Fix

Re-baseline heap settings explicitly rather than inheriting ergonomic defaults across the migration: set `-XX:MaxRAMPercentage` (or `-Xmx`) deliberately per service, sized against the container limit you actually grant it. The JVM default remains 25% of the limit — unchanged through JDK 25, despite published claims to the contrary (Chapter 1.5 has that story) — which is conservative for a single-JVM container; many teams legitimately run 50–75%, but that should be a decision, not an inheritance. While you're there, kill any remaining `UseCGroupMemoryLimitForHeap` flags: the experimental JDK-8-era opt-in was removed once the real support landed, and it's a startup failure on modern JDKs.

## Worked example

From [`examples/37-container-memory-ergonomics`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/37-container-memory-ergonomics), verified on Temurin 8u502 and Temurin 25.0.4 under a real cgroup v1 memory limit (no container runtime needed):

```
Host total memory: 7.8Gi

JDK 8 MaxHeapSize, unconstrained:            := 2103443456        (~2GB, 25% of host)
JDK 8 MaxHeapSize, 512MB cgroup:             := 134217728         (128MB, 25% of limit)

JDK 25 MaxHeapSize, unconstrained:            = 2103443456        (identical)
JDK 25 MaxHeapSize, 512MB cgroup:             = 134217728         (identical)
```

Byte-for-byte identical ergonomics on both sides of the migration — the 8u191 backport, confirmed. The story to verify in *your* estate is the age of your images, not the behaviour of current JDKs.
