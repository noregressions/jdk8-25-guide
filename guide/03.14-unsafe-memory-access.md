`sun.misc.Unsafe` dates from 2002 as the JDK's internal toolbox for low-level operations — atomic compare-and-swap on fields, off-heap allocation, constructor bypass. It was never a public API, but nothing prevented outside use, and the high-performance ecosystem — Netty, Guava, Caffeine, Kryo, the LMAX Disruptor — built critical fast paths on it. Of its 87 methods, 79 are memory-access methods, and those 79 are what the JDK is now evicting.

---

## The eviction timeline

The eviction is a staged squeeze, and knowing which stage you are in determines the urgency:

| Stage | Release | What happens |
|---|---|---|
| Replacements exist | JDK 9 (`VarHandle`), JDK 22 (FFM) | Standard APIs cover the legitimate uses |
| Terminal deprecation | JDK 23 (JEP 471) | All 79 methods `forRemoval=true` |
| Runtime warnings | **JDK 24** (JEP 498) | First use per method warns on stderr, `warn` is the default |
| Exceptions | A future release | Default flips to `deny`; every call throws `UnsupportedOperationException` |
| Removal | Later still | `NoSuchMethodError` |

Two precision points that most write-ups get wrong. The warnings began in **JDK 24**, not 25. And the exception phase has **not yet shipped**: JEP 498 committed only to "JDK 26 or later", and JDK 26 (March 2026) arrived still warn-only — so the deadline is real but unscheduled. Plan as if the next release flips it; the `=deny` flag lets you live there today.

Also note the scope: this timeline covers the 79 memory-access methods. The other eight (`allocateInstance`, `throwException`, and friends) are on a separate track, and the class itself is not disappearing yet.

---

## Why you care even if you never wrote `Unsafe`

The usage that breaks applications is overwhelmingly in third-party libraries. Maven itself, run on JDK 24, warns from Guava's `AbstractFuture$UnsafeAtomicHelper` calling `objectFieldOffset`. NetBeans triggers the same Guava warning at startup. JavaFX's Marlin rasterizer uses `Unsafe::allocateMemory`. The OpenTelemetry Java SDK warns on initialisation. Your build tool is calling Unsafe.

Most major libraries have already migrated — Guava, Netty, and Caffeine ship `VarHandle`-based paths selected automatically on modern JDKs — but the version *in your tree* may predate the fix, and the libraries three levels down may never have been fixed at all. This category is a dependency-freshness problem wearing a JVM costume.

---

## Detect

Layered, cheapest first:

```bash
jdeps --jdk-internals --class-path 'libs/*' app.jar          # static: who references Unsafe
java --sun-misc-unsafe-memory-access=debug -jar app.jar      # runtime: full stack trace on EVERY call
java --sun-misc-unsafe-memory-access=deny  -jar app.jar      # CI: simulate the future default
```

`debug` is the migration workhorse — unlike `jdeps`, it catches reflective acquisition of the Unsafe singleton (the standard pattern, and one static analysis cannot see). `deny` belongs in CI once you are clean: if a dependency update reintroduces Unsafe, the build fails immediately instead of accumulating warnings nobody reads. `allow` exists as a documented escape hatch — the awkward middle for a dependency you cannot yet move off — and should carry a tracking issue like any other workaround flag.

---

## Fix

Upgrade the dependencies doing the calling — that is the whole fix in most applications. Where the code is yours, the mappings are mechanical:

- **On-heap atomics** — `UNSAFE.compareAndSwapInt(this, OFFSET, expect, update)` becomes a `VarHandle` and `HANDLE.compareAndSet(this, expect, update)`. `VarHandle` also recomputes field offsets correctly under layout changes, which cached Unsafe offsets do not — that interaction with compact object headers is Chapter 3.20, and it is the reason "works today with warnings" can still mean "corrupts data under a JDK 25 feature flag."
- **Off-heap memory** — `allocateMemory`/`freeMemory` becomes the FFM API: `try (Arena arena = Arena.ofConfined()) { ... }` with allocation scoped to the arena's lifetime.

## Worked example

From `discovery-tests/14-unsafe-memory-access-warning`, verified on Temurin 8u502 and Temurin 25.0.4 — the standard reflective-singleton pattern calling `objectFieldOffset` + `putInt`, three ways:

```
JDK 8:
  h.x via Unsafe = 42
  exit=0

JDK 25 (default):
  WARNING: A terminally deprecated method in sun.misc.Unsafe has been called
  WARNING: sun.misc.Unsafe::objectFieldOffset has been called by UnsafeTest (file:...)
  WARNING: sun.misc.Unsafe::objectFieldOffset will be removed in a future release
  h.x via Unsafe = 42
  exit=0

JDK 25 with --sun-misc-unsafe-memory-access=deny (simulating the future default):
  Exception in thread "main" java.lang.UnsupportedOperationException: objectFieldOffset
      at jdk.unsupported/sun.misc.Unsafe.beforeMemoryAccessSlow(Unsafe.java:1822)
      at jdk.unsupported/sun.misc.Unsafe.objectFieldOffset(Unsafe.java:905)
      at UnsafeTest.main(UnsafeTest.java:8)
  exit=1
```

The third run is tomorrow, available today. Teams that put it in CI find out about regressions from a build failure; everyone else finds out from a release note.
