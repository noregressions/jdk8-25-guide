| **Introduced** | Cumulative across 17 releases — no single JEP. A representative newcomer: the `this-escape` lint (JDK 21) |
| **Symptom** | `error: warnings found and -Werror specified` — on identical source that compiled cleanly with identical flags on JDK 8 |
| **Detect** | Trial-compile against the target JDK; triage what `-Xlint` now reports before deciding what `-Werror` covers |

```
ThisEscape.java:9: warning: [this-escape] possible 'this' escape before subclass is fully initialized
error: warnings found and -Werror specified
```

`-Werror` is a bet that your warning set is stable. Between JDK 8 and 25 it wasn't: each release taught `javac` new things to notice — new lint categories, new deprecations, terminal deprecations of things merely deprecated before. A build with `-Xlint:all -Werror` that has been green for a decade is green against 2014's opinions; the first recompile on JDK 25 applies 2026's.

---

## What happened

Nothing is wrong with the code in the failing example — and something *is* worth hearing in the warning, which is what makes this category more interesting than a nuisance. The verified case uses JDK 21's `this-escape` lint: a constructor calling an overridable method, which a subclass override can receive **before the subclass's own fields are initialised**. That is a real bug class that JDK 8's compiler simply couldn't see. Multiply by every category added across seventeen releases and the migration recompile becomes, in effect, a free static-analysis upgrade that your `-Werror` policy converts into a build failure.

The failure mode to avoid is social, not technical: a wall of new warnings on migration day, a deadline, and someone deleting `-Werror` "temporarily". Now the policy that kept the build warning-clean for years is gone, at the precise moment the compiler got smarter.

---

## Detect

Trial-compile with your real flags on the target JDK, early — before the migration branch, not on it:

```bash
javac --release 25 -Xlint:all -Werror -d /tmp/trial $(find src -name "*.java") 2>&1 | \
  grep -oE "\[[a-z-]+\]" | sort | uniq -c | sort -rn
```

That histogram — which categories, how many of each — is the entire triage input, and it turns "the build is red" into a fixed-size work list.

---

## Fix

Per category, in preference order: **fix** the code where the warning found something real (`this-escape` findings often qualify); **suppress precisely** where it's a deliberate pattern — `@SuppressWarnings("this-escape")` at the narrowest scope, with a comment; **exclude the category** from the lint set (`-Xlint:all,-this-escape`) only where a category genuinely doesn't fit the codebase, recorded in the build file where the next reader sees it.

What not to do is blanket-disable `-Werror`. The policy is worth more after this migration than before it — it is now enforcing seventeen releases' worth of better analysis.

---

## Worked example

From `discovery-tests/30-stricter-javac-werror-builds`, verified on Temurin 8u502 and Temurin 25.0.4 — identical two files, identical `-Xlint:all -Werror` flags. The test class is deliberately a *true positive*: the constructor calls an overridable method, and the subclass override reads its own field, demonstrating why the lint exists:

```
JDK 8, -Xlint:all -Werror:
  exit=0

JDK 25, -Xlint:all -Werror (identical source, identical flags):
  ThisEscape.java:9: warning: [this-escape] possible 'this' escape before subclass is fully initialized
          doSomething();
  error: warnings found and -Werror specified
  exit=1
```

`this-escape` is the specimen, not the story — any of the dozens of categories added across JDK 9–25 produces the same shape against a never-trial-compiled `-Werror` build.
