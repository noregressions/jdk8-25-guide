| **Level** | Recompilation Surprises |
| **Introduced** | JDK 9 (JEP 213 — `_` reserved as a keyword); JDK 22 (JEP 456 — repurposed as the unnamed variable) |
| **Symptom** | Compile error: `underscore not allowed here` |
| **Detect** | Recompile against the target JDK — the compiler names every occurrence |

```
Underscore.java:4: error: underscore not allowed here
        System.out.println("value=" + _);
                                      ^
```

A single-character variable name, legal since Java 1.0, became a reserved keyword in JDK 9 — and in JDK 22 was given its new job as the *unnamed variable* (`var _ = ...` for values you're required to bind but don't want). Code that used `_` as an ordinary identifier — loop counters, lambda parameters in terse styles, generated code — recompiles with a hard error.

---

## What happened

This chapter earns its place less for its blast radius (small, easily fixed) than for being the cleanest possible demonstration of the principle this whole level rests on. The verified sequence tells the entire story of the *recompilation paradox*:

1. `javac8` compiles `int _ = 42;` — with a warning, which is worth noticing: JDK 8 was already announcing this future in 2014.
2. The resulting class file runs on JDK 8. It runs, **unmodified, on JDK 25** — bytecode has no opinion about identifier fashion; the name is just a string in a local-variable table.
3. The *same source* fed to `javac25` fails outright.

Old binaries and recompiled binaries are two different populations with two different failure sets. A migration test plan that only exercises one of them — usually the "does the old JAR still run" half — certifies half the risk. That is the rule to carry into every chapter of this level, delivered here by the smallest possible example.

---

## Detect

The compiler is the detector, and it is exhaustive: trial-compile on the target JDK and every occurrence is named with file and line. If you want a preview without a full toolchain switch:

```bash
grep -rEn "\b_\s*=|\(\s*_\s*[,)]|\b(int|long|String|var)\s+_\b" src/
```

but the trial compile is the answer that can't miss. Generated code deserves a specific look — some JDK-8-era code generators emitted `_`-prefixed or bare-`_` locals as a style.

---

## Fix

Rename the identifier — `unused`, `ignored`, or something meaningful. That's the whole fix.

One forward-looking note: on JDK 22+, `_` as an *unnamed* variable is not just legal but idiomatic for exactly the cases old code used it for — "I must bind this but don't care":

```java
try (var _ = lock.acquire()) { ... }        // JDK 22+ unnamed variable
```

So the identifier comes back — but as a declaration you can never *read* from. The old code's mistake wasn't the name; it was reading it.

---

## Worked example

From [`examples/26-underscore-as-identifier`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/26-underscore-as-identifier), verified 2026-08-07 on Temurin 8u502 and Temurin 25.0.4:

```
$ javac8 Underscore.java
Underscore.java:3: warning: '_' used as an identifier
  (use of '_' as an identifier might not be supported in releases after Java SE 8)
COMPILED OK

$ java8 Underscore       # old binary, old JVM
value=42

$ java25 Underscore      # SAME .class file, JDK 25 — runs fine
value=42

$ javac25 Underscore.java
Underscore.java:4: error: underscore not allowed here
1 error
```

The binary never breaks. Only the recompile does.
