```
$ ls $JDK25_HOME/jre              -> No such file or directory
$ ls $JDK25_HOME/lib/tools.jar    -> No such file or directory
```

This level of the catalogue is about failures that happen *around* the application rather than in it, and this chapter is its purest representative: often the first thing to break in a migration, before any runtime category gets the chance, and it doesn't even fail in Java — it fails as a missing file in a shell script.

---

## What happened

JEP 220 replaced the JDK's file-based runtime with modular images. Three landmarks a generation of tooling navigated by all vanished at once: `rt.jar` (the entire platform's classes — gone into the modular image, readable via the `jrt:` filesystem instead), `tools.jar` (the compiler and tool APIs — now proper modules like `jdk.compiler`), and the nested `jre/` directory (there is no bundled JRE-inside-a-JDK anymore; the JDK's own top level *is* the runtime).

Where the assumptions hide: build scripts adding `tools.jar` to a classpath to reach `javac` internals or the attach API; static-analysis and coverage configs pointing at `rt.jar` as the boot classpath; installers and service wrappers resolving `$JAVA_HOME/jre/bin/java`; IDE run configurations and ancient Ant files. None of these are Java code, so no Java-side analysis finds them.

---

## Detect

```bash
grep -rE "rt\.jar|tools\.jar|/jre/|jre/bin" build.xml pom.xml *.gradle scripts/ ci/ Dockerfile*
```

Include vendor-supplied wrapper scripts and monitoring-agent configs — the 2000s-era ones are the likeliest carriers.

---

## Fix

Each landmark has a modern equivalent: code that loaded `tools.jar` to reach the compiler uses the standard `javax.tools.ToolProvider` / `java.util.spi.ToolProvider` APIs, which need no classpath surgery at all; anything scanning `rt.jar` to enumerate platform classes uses the `jrt:` filesystem (`FileSystems.getFileSystem(URI.create("jrt:/"))`); and every `$JAVA_HOME/jre/...` path becomes plain `$JAVA_HOME/...`. Scripts that must serve both JDKs during the transition can branch on the existence of the `jre/` directory — one of the few version probes that is actually reliable (Chapter 3.23 covers the unreliable kind).

## Worked example

From `discovery-tests/32-jdk-layout-changed`, verified 2026-08-07 on Temurin 8u502 and Temurin 25.0.4 — a pure filesystem check:

```
$ ls $JDK8_HOME
ASSEMBLY_EXCEPTION  LICENSE  NOTICE  THIRD_PARTY_README  bin  include  jre  lib  man  release  sample  src.zip
$ ls $JDK8_HOME/jre/lib/rt.jar     -> exists
$ ls $JDK8_HOME/lib/tools.jar      -> exists

$ ls $JDK25_HOME
NOTICE  bin  conf  include  legal  lib  man  release
$ ls $JDK25_HOME/jre               -> No such file or directory
$ ls $JDK25_HOME/lib/rt.jar        -> No such file or directory
$ ls $JDK25_HOME/lib/tools.jar     -> No such file or directory
```

Even the top-level listing tells the story — the modern JDK has fewer, different directories (`conf/` and `legal/` are themselves JDK 9+ arrivals worth knowing when scripts go looking for configuration).
