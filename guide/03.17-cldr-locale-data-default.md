| | |
|---|---|
| **Level** | Runs But Wrong |
| **Introduced** | JDK 9 (JEP 252) |
| **Symptom** | Formatted dates, currencies, numbers, and era names change silently — worst for *stored* formatted output: report filenames, invoices, log timestamps, generated documents |
| **Detect** | Run locale-sensitive tests on both JDKs and diff the output |

No exception in this chapter either. The failure is three extra characters:

```
JDK 8:  full date ja_JP → 9 characters, no day-of-week
JDK 25: full date ja_JP → 12 characters, day-of-week appended
```

JDK 8 formatted dates, numbers, and currencies from its own bundled locale data (the "COMPAT" provider). JDK 9 switched the default to the Unicode Consortium's CLDR — the industry-standard locale dataset, and a genuinely better one. But "better" here means *different*, across thousands of locale/format combinations: date element order, separator characters, month and day names, first-day-of-week, currency symbol placement, era formatting.

---

## What happened

JEP 252 changed which provider answers every locale-sensitive formatting call, application-wide, with no code change and no warning. The formats are not wrong afterwards — CLDR is usually *more* correct by the standards of each locale — but they no longer match what your JDK 8 application produced, and three classes of code care deeply:

- **Tests asserting exact formatted strings.** These fail visibly, which makes them the lucky case.
- **Stored formatted output.** Invoices, report filenames, exported CSVs, anything a downstream system parses with an expectation of the old shape. The producer changes format; the consumer breaks later, elsewhere, mysteriously.
- **Round-trip code** that formats with one JDK's rules and parses with the other's — the migration period itself is the danger window.

The changes are locale-specific and irregular: as the worked example shows, the same locale's currency format can be untouched while its date format changes. There is no summary of "what changed" to review — the practical answer is empirical comparison of *your* output.

---

## Detect

Run your locale-sensitive test suite on both JDKs and diff. If you don't have one, this category is the argument for building it: a small harness that formats representative dates/numbers/currencies across the locales you actually serve, run on both JDKs, diffed. Cheap to write, and it converts an invisible risk into a reviewable list.

```bash
grep -rEn "DateFormat|NumberFormat|SimpleDateFormat|DateTimeFormatter.ofLocalized|String.format.*%t" src/
```

flags the call sites; pay closest attention to any whose output is written to disk or sent to another system.

---

## Fix

The structural fix: stop treating formatted strings as data. Store and transmit structured types (`LocalDate`, `Instant`, amounts as numbers plus currency codes) and format only at the display boundary — then the formatting rules can change without anything downstream caring. Where a specific external format is contractual (a bank file, a regulatory report), pin it with an explicit pattern rather than a locale default: `DateTimeFormatter.ofPattern(...)` produces what you specify on any JDK.

The bridge, not the fix: `-Djava.locale.providers=COMPAT,CLDR` restores JDK 8 behaviour while you work through the list. Like every compatibility flag in this guide it deserves a tracking issue and a removal date — the COMPAT data is frozen in time and only drifts further from reality.

## Worked example

From `discovery-tests/17-cldr-locale-data-default`, verified on Temurin 8u502 and Temurin 25.0.4 — `2019-05-02` formatted FULL-style for `Locale.JAPAN`:

```
JDK 8 (COMPAT provider, the JDK 8 default):
  currency ja_JP = ¥1,234
  full date ja_JP = year+month+day in kanji — 9 characters, no day-of-week
  full date length (chars) = 9

JDK 25 (CLDR provider, the JDK 9+ default):
  currency ja_JP = ¥1,234
  full date ja_JP = the same, PLUS the day-of-week name — 12 characters
  full date length (chars) = 12
```

Same input, same locale, same API call. The currency happened to agree in this combination; the date grew a day-of-week name. Neither run logged anything. Now imagine the 9-character version is embedded in five years of generated report filenames, and the parser that reads them.
