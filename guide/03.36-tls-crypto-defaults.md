Security posture is the JDK's most continuously moving surface: nearly every release extends `jdk.tls.disabledAlgorithms`, retires a signature algorithm, or hardens a default. For a migration guide the honest framing is unusual — this is the one category where the "before" side is itself a moving target.

---

## What happened — and the patch-level caveat that changes the story

The verified comparison produced a finding more useful than the folklore. The folklore says "JDK 8 allows weak TLS; JDK 25 doesn't." The measurement says: a **current** JDK 8 patch (Temurin 8u502) *already* disables `SSLv3`, `TLSv1`, and `TLSv1.1` by default — because TLS hardening is backported into ongoing 8u security updates, not introduced fresh in later majors. JDK 25's disabled list is longer (DTLS, `TLS_RSA_*` suites, SHA-1 handshake signatures), but it extends an already-hardened baseline rather than contradicting a permissive one.

The migration consequence cuts both ways. If your JDK 8 estate is *patched current*, most TLS breakage already happened to you quietly over the years, and 25 adds increments. If your estate is a **frozen, years-old 8u build** — which unpatched production systems often are — then the migration delivers the entire accumulated hardening at once, and every legacy endpoint, old appliance, and internal service with a 2015-era TLS stack fails in the same week. Know which estate you have before predicting this category's blast radius.

The one clean, patch-independent pin: the default keystore type changed from JKS to PKCS12 in JDK 9. Code and scripts that create keystores without an explicit type now produce a different format — usually harmless (JKS files remain readable), occasionally surprising to tooling that inspects types. Alongside it, SHA-1-signed JARs are progressively treated as unsigned on modern JDKs — old vendor JARs with ancient signatures lose whatever their signature was granting.

---

## Detect

Integration tests against *every* TLS endpoint the application touches, run on the target JDK — including the internal ones nobody lists: LDAP servers, mail relays, payment appliances, database TLS. For triage on a failing handshake:

```bash
java -Djavax.net.debug=ssl:handshake -jar app.jar     # verbose but definitive
grep -rn "keystore.type\|KeyStore.getInstance" src/    # explicit vs default types
```

And compare the two JDKs' actual policies directly: `java.security` ships in `conf/security` (JDK 9+ layout — Chapter 3.32) and the diff of `jdk.tls.disabledAlgorithms` between your real 8 build and 25 is your real delta.

---

## Fix

Fix endpoints, not the JDK, wherever you control them — upgrading a legacy service's TLS config is work that was due anyway. Re-sign old JARs with SHA-256+. Declare keystore types explicitly where tooling cares. The escape hatch — re-enabling algorithms by editing `jdk.tls.disabledAlgorithms` — exists and is occasionally unavoidable for a vendor appliance on a replacement timeline; treat each such edit as a security exception with an owner and an expiry, because that is literally what it is.

## Worked example

From [`examples/36-tls-crypto-keystore-defaults`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/36-tls-crypto-keystore-defaults), verified on Temurin 8u502 and Temurin 25.0.4. The keystore default is asserted; the TLS lists are recorded rather than asserted, for the reason above:

```
Default keystore type:
  JDK 8:  keystore.type = jks
  JDK 25: keystore.type = pkcs12

jdk.tls.disabledAlgorithms (informational):
  JDK 8:  SSLv3, TLSv1, TLSv1.1, RC4, DES, MD5withRSA, DH keySize < 1024, ...
  JDK 25: SSLv3, TLSv1, TLSv1.1, DTLSv1.0, RC4, DES, MD5withRSA, ..., TLS_RSA_*,
          rsa_pkcs1_sha1/ecdsa_sha1/dsa_sha1 usage HandshakeSignature
```

Both lists already ban TLSv1/1.1 — the "before" in this sandbox is a 2026-patched JDK 8, and that is exactly the point worth carrying on stage: cite this category's before/after only after checking which 8u your audience is actually running.
