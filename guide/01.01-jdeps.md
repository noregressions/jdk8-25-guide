---

`jdeps` ships with the JDK, costs nothing to run, and will tell you more about your migration risk in ten minutes than a week of manual code review. Most teams have never used it. That changes now.

It analyses compiled bytecode — your class files and JARs — and reports every dependency on JDK internal APIs: the `sun.*`, `com.sun.*`, and `jdk.internal.*` packages that the module system has progressively walled off, and which are now either hard errors or on the removal path. Run it before you change a single line of code.

---

## What it finds

`jdeps` finds **declared dependencies** — the symbolic references baked into compiled class files. That covers:

- Direct usage of JDK internal APIs in your own code
- Internal API usage in third-party JARs on your classpath
- Module system issues: split packages, missing module dependencies, and unnamed module warnings
- References to packages removed from the JDK (the Java EE modules removed in JDK 11)
- Native access patterns that require `--enable-native-access`

The most important use case is `--jdk-internals`. Run it on your code and on every JAR in your classpath. The internal API usage that will break your migration is often three levels deep in the dependency tree, in a library your code never references directly.

---

## What it misses

`jdeps` analyses what the bytecode *declares*. It cannot see what the code *does at runtime*.

It will not find:
- Reflective access to internal APIs via `Class.forName()`, `getDeclaredField()`, or `setAccessible(true)`
- Dynamic class loading
- Internal APIs loaded from string literals at runtime
- Behaviour changes that don't involve an API call at all (charset defaults, locale formatting, GC differences)

This is not a flaw in the tool. It's a fundamental property of static analysis. `jdeps` is your first pass, not your only pass. Chapter 1.6 covers the runtime tools that catch what `jdeps` misses.

## Key flags

| Flag | Purpose |
|------|---------|
| `--jdk-internals` | Reports all dependencies on JDK internal APIs. The flag you will use most. |
| `--class-path` | Specifies the classpath for analysis. Include all your application JARs and dependencies. |
| `--module-path` | Specifies the module path. Use this if your application runs on the module path. |
| `--multi-release <version>` | Analyses multi-release JARs using the class files for the specified JDK version. |
| `-R` / `--recursive` | Recursively analyses transitive dependencies. Use with caution on large classpaths — the output grows fast. |
| `--ignore-missing-deps` | Suppresses warnings for unresolvable dependencies. Useful when analysing a single JAR without its full classpath. |
| `-verbose:class` | Shows class-level dependency detail rather than package-level summaries. |
| `--print-module-deps` | Prints the module dependencies of the analysed code. Useful for `module-info.java` generation. |

---

## The `--multi-release` trap

Many popular libraries — Guava, Apache Commons, Jackson — now ship as multi-release JARs. These contain version-specific class files at paths like `META-INF/versions/11/` that override the baseline classes when running on the corresponding JDK.

Without `--multi-release`, `jdeps` scans the baseline (JDK 8) class files. Those often contain internal API usages that the versioned files have already replaced. You end up chasing problems that do not exist on your target JDK.

Always run with `--multi-release 25` (or whatever your target) when scanning modern libraries.

## Worked example

A typical analysis run against an application JAR with its dependencies:

```bash
jdeps \
  --jdk-internals \
  --multi-release 25 \
  --class-path 'libs/*' \
  myapp.jar
```

Illustrative output (a clean JAR simply produces no findings — the annotation shown for Guava below is added for clarity):

```
myapp.jar -> java.base
myapp.jar -> jdk.unsupported
   com.example.cache.OffHeapStore       -> sun.misc.Unsafe
      (JDK internal API (jdk.unsupported))
   com.example.xml.LegacyMarshaller     -> com.sun.xml.internal.bind.v2.ContextFactory
      (JDK internal API (java.xml.bind))
   com.example.util.ReflectionHelper    -> sun.reflect.ReflectionFactory
      (JDK internal API (java.base))

libs/guava-31.0.jar -> java.base
   (no internal API usage at release 25)

libs/legacy-vendor-utils-2.3.jar -> java.base
   com.example.vendor.StringUtils       -> sun.misc.Unsafe
      (JDK internal API (jdk.unsupported))
```

Working through this output:

**`com.example.cache.OffHeapStore -> sun.misc.Unsafe`**
Your own code is calling `sun.misc.Unsafe` directly. This is a declared bytecode dependency, not a reflective one — `jdeps` can see it. The `(jdk.unsupported)` annotation means the class is technically accessible via the `jdk.unsupported` module for now, but `Unsafe` memory-access methods are deprecated for removal. Chapter 3.14 covers the migration path to `VarHandle` and the Foreign Function & Memory API.

**`com.example.xml.LegacyMarshaller -> com.sun.xml.internal.bind.v2.ContextFactory`**
Your code is using internal JAXB classes rather than the public API. The annotation `(java.xml.bind)` references the module that was removed in JDK 11. This class no longer exists on JDK 25. Chapter 3.6 covers the replacement dependencies.

**`com.example.util.ReflectionHelper -> sun.reflect.ReflectionFactory`**
An internal reflection factory. This was encapsulated in JDK 9 and will throw `InaccessibleObjectException` when accessed without an `--add-opens` flag. Chapter 3.5 covers this failure mode.

**`guava-31.0.jar -> (no internal API usage at release 25)`**
The `--multi-release 25` flag picked up the JDK 25 class files inside the Guava multi-release JAR. No issues at this version. Without this flag, older Guava versions report false positives from their JDK 8 baseline classes.

**`legacy-vendor-utils-2.3.jar -> sun.misc.Unsafe`**
A transitive dependency using `Unsafe`. Your code doesn't call `legacy-vendor-utils` directly in this code path, but the library is on your classpath and will trigger `Unsafe` warnings at runtime. Check whether a newer version of `legacy-vendor-utils` has removed this usage before treating it as a blocker.

## Interpreting the output

Not all `jdeps` findings are equal. A useful triage approach:

**Immediate blockers** are internal API usages where the API no longer exists on JDK 25. The Java EE packages (`javax.xml.bind.*`, `javax.annotation.*`, `javax.xml.ws.*`) are the clearest examples. These produce `NoClassDefFoundError` at runtime. Fix before anything else.

**Serious warnings** are usages of encapsulated internal APIs that exist but are inaccessible by default on JDK 17 and later. `sun.reflect.*`, `com.sun.tools.*`, internal JDK classes. These produce `InaccessibleObjectException` at runtime unless you add `--add-opens` workarounds. The workaround is temporary; the fix is upgrading the dependency or patching the code.

**Deprecation risks** are usages of APIs that still exist but are deprecated for removal. `sun.misc.Unsafe` memory-access methods are the primary example. They work on JDK 25, produce warnings, and will throw on a future JDK. Plan the migration but they are not blockers today.

**False positives to ignore** are findings in the JDK 8 baseline classes of multi-release JARs that have already been fixed in the versioned classes. Always use `--multi-release` to filter these out.

One final point on scope: run `jdeps` against your *transitive* dependencies. A project with 30 declared dependencies may have 180 or more JARs on its full classpath. The internal API usage you need to worry about is often in a library that nothing in your source code references directly. The `-R` flag does this recursively, but the output volume on a large project can be overwhelming. An alternative is to extract your full dependency list with `mvn dependency:copy-dependencies` and point `jdeps` at the resulting directory.
