This category has a split personality, and the worked example shows both faces:

```
JDK 25, default:                          runs fine
JDK 25, with -XX:+UseBiasedLocking:       Unrecognized VM option 'UseBiasedLocking'
                                          Error: Could not create the Java Virtual Machine.
```

Biased locking was a HotSpot optimisation from the JDK 1.5 era: it made *uncontended* `synchronized` nearly free by biasing each monitor toward the first thread that took it. It existed because early-2000s code synchronised everything — `Vector`, `Hashtable`, `StringBuffer`, single-threaded use of thread-safe classes — and it made that style cheap.

---

## What happened

JEP 374 disabled biased locking by default and deprecated its flags in JDK 15: the bookkeeping (bias revocation, safepoint coordination) had grown expensive relative to its benefit on modern hardware and modern code, and it complicated every other improvement to synchronisation. JDK 18 removed the implementation and obsoleted the flag (JDK-8256425); the flag expired in JDK 19. From then on, `-XX:+UseBiasedLocking` isn't a rejected request — it's an unknown word, and unknown `-XX:` options are startup-fatal (Chapter 3.1's rule).

Hence the two audiences:

**Teams without the flag** get the silent version: uncontended `synchronized` costs a little more than it did on JDK 8. For most applications this vanishes into noise. Where it can show up as a measurable throughput regression is precisely the legacy profile — hot paths dominated by single-threaded use of `StringBuffer`, `Vector`, `Hashtable`, or heavily-synchronised frameworks of the same vintage. No error, no log line; just a benchmark delta whose cause is invisible without knowing this history.

**Teams with the flag** — and explicitly enabling biased locking was a *standard published tuning recommendation* for lock-heavy workloads for years — get a dead JVM. A config line that was best practice when written is now a startup failure, which is why this chapter cross-files itself under Won't Start.

---

## Detect

```bash
grep -rE "UseBiasedLocking|BiasedLocking" deploy/ docker/ k8s/ *.sh *.conf
```

That's the fatal half, and it belongs in the Chapter 1.5 flag audit. The performance half has no grep: it is a JFR baseline comparison (Chapter 1.6) between JDKs under real load, looking at throughput and `synchronized`-heavy hot paths. Suspect it specifically when a lock-heavy legacy service benchmarks a few percent slower with no other explanation.

---

## Fix

Remove the flag — that part is non-negotiable and free. For the performance side, correctness needs nothing: `synchronized` semantics are unchanged. If measured throughput actually matters on an affected path, the durable fix is the one that was already overdue: replace single-threaded use of `StringBuffer` with `StringBuilder`, `Vector`/`Hashtable` with `ArrayList`/`HashMap`, and genuinely concurrent structures with `java.util.concurrent` — removing the pointless synchronisation instead of mourning the optimisation that made it tolerable.

---

## Worked example

From `discovery-tests/24-biased-locking-removed`, verified on Temurin 8u502 and Temurin 25.0.4 — an uncontended `synchronized` loop under four configurations:

```
JDK 8, default:
  uncontended synchronized loop completed, counter=2000000     exit=0

JDK 8, with -XX:+UseBiasedLocking explicitly (a common JDK-8-era tuning flag):
  uncontended synchronized loop completed, counter=2000000     exit=0

JDK 25, default:
  uncontended synchronized loop completed, counter=2000000     exit=0

JDK 25, with the SAME flag carried forward from the JDK 8 config:
  Unrecognized VM option 'UseBiasedLocking'
  Error: Could not create the Java Virtual Machine.
  exit=1
```

The test deliberately asserts on startability, not timing — an uncontended-lock micro-benchmark in a shared sandbox would be noise dressed as data. The deterministic finding is the one that matters operationally: three of these four configurations run, and the fourth is a JDK 8 best practice.
