| | |
|---|---|
| **Level** | Runs But Wrong |
| **Introduced** | JDK 18 (JEP 400) |
| **Symptom** | Silent misreading of files written under the old platform default — overwhelmingly a Windows problem (windows-1252, windows-31j); macOS and Linux already defaulted to UTF-8 |
| **Detect** | Search for `FileReader`, `FileWriter`, `InputStreamReader`, `OutputStreamWriter`, `new String(byte[])`, `String.getBytes()` without an explicit charset |

Here is the failure at byte level — a `£` sign written on JDK 8, read back on JDK 25:

```
JDK 8 wrote:  50 72 69 63 65 20 A3 31 30 30    ("Price £100", £ as one windows-1252 byte)
JDK 25 read:  char[6] = U+FFFD                  (the Unicode replacement character)
```

No exception on the write. No exception on the read. Just `�` where money used to be.

---

## What happened

Before JDK 18, every no-charset I/O call — `new FileReader(f)`, `new String(bytes)`, `getBytes()` — used the *platform* default, which meant UTF-8 on macOS and Linux but windows-1252 (or windows-31j in Japan) on most Windows machines. JEP 400 ended the lottery: from JDK 18 the default charset is UTF-8 everywhere, unconditionally.

The crucial subtlety — which an earlier version of this guide's own test got wrong, instructively — is that the risk is **cross-version, not same-process**. A JDK 25 application that writes and reads its own files agrees with itself perfectly. What breaks is *history*: every file written by the JDK 8 application under the old default, sitting on disk, in archives, in attachments — now misread by the migrated reader. Accented names, currency symbols, umlauts: each non-ASCII byte decodes to `U+FFFD`, and if the corrupted string is then *saved*, the damage becomes permanent and spreads.

The deployment asymmetry makes it worse: development on macOS, CI on Linux — both already UTF-8, so nothing ever fails before production. The one environment that breaks is the Windows production estate, which is precisely the environment the test pyramid touches last.

---

## Detect

```bash
grep -rEn "new FileReader\(|new FileWriter\(|new InputStreamReader\([^,)]*\)|new OutputStreamWriter\([^,)]*\)|\.getBytes\(\)|new String\(\s*[a-zA-Z_]+\s*\)" src/
```

Every hit without a charset argument is a call site trusting a default that changed. For the data side, inventory what the application *reads that it did not just write*: long-lived files, imports, anything user-uploaded — and establish what encoding that history actually is.

---

## Fix

Make every call site explicit: `StandardCharsets.UTF_8` where the data genuinely is UTF-8, and — the part teams miss — **the old charset by name** where the data is legacy: `new InputStreamReader(in, "windows-1252")` is the *correct* code for reading a windows-1252 archive, on any JDK, forever. Explicitness is the fix; UTF-8-everywhere is merely the usual conclusion.

The bridge: `-Dfile.encoding=COMPAT` restores pre-JDK 18 behaviour while the call sites are worked through. Standard rules apply — tracking issue, removal date. For bulk conversion of legacy data, convert once, deliberately, with a tool that knows both encodings, rather than letting ad-hoc reads decide.

---

## Worked example

From `discovery-tests/18-utf8-default-charset`, verified 2026-08-07 on Temurin 8u502 and Temurin 25.0.4. The writer runs under JDK 8 with `-Dfile.encoding=windows-1252` forced — simulating the historically affected Windows platform deterministically — and writes `"Price £100"` via `FileWriter` with no charset. The reader runs under JDK 25 with its own unforced default:

```
$ java8 -Dfile.encoding=windows-1252 Write8
writer file.encoding = windows-1252
bytes written (10): 50 72 69 63 65 20 A3 31 30 30      <- £ as a single windows-1252 byte

$ java25 Read25
reader file.encoding = UTF-8
read back: matches original = false
read back char[6] = U+FFFD                              <- the Unicode replacement character
```

The write emitted no warning in 2015-era production, and none in this test. The corruption exists only in the gap between what byte `0xA3` meant then and what it means to a UTF-8 decoder now. Re-run under a forced UTF-8 host locale, the result is identical — the failure depends only on the file's history, not the machine's mood.
