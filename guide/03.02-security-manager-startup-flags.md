| | |
|---|---|
| **Level** | Won't Start |
| **Introduced** | JDK 24 (JEP 486). The *runtime call* fails earlier — by default since JDK 18 — but the startup flag is VM-init-fatal only from 24 (Chapter 3.8) |
| **Symptom** | `Error occurred during initialization of VM` — the JVM exits before `main()` |
| **Detect** | Audit startup scripts and Docker entrypoints for `-Djava.security.manager` |

The Security Manager's removal breaks applications three different ways, and this is the bluntest of them:

```
Error occurred during initialization of VM
java.lang.Error: A command line option has attempted to allow or enable the
Security Manager. Enabling a Security Manager is not supported.
```

On JDK 8, `-Djava.security.manager` on the command line simply opted in to a standard platform feature. Legacy app servers, RMI deployments, and security-conscious ops teams put it there deliberately. From JDK 24 (JEP 486, which permanently disabled the Security Manager), the same flag stops the VM during initialisation.

---

## What happened

The timeline matters because it is widely misquoted. The Security Manager was deprecated for removal in JDK 17 (JEP 411). From JDK 18, `disallow` became the default value of `java.security.manager`, so *code* calling `System.setSecurityManager()` already threw `UnsupportedOperationException` unless the deployment explicitly passed `-Djava.security.manager=allow` — that escape hatch existed through JDK 23 and is covered in Chapter 3.8. JDK 24 removed the machinery entirely: attempting to allow or enable a Security Manager from the command line is now a VM-initialisation error, and there is no flag, property, or workaround that restores it.

This is a harder failure than its runtime sibling. When `setSecurityManager()` throws from code, you get a stack trace in your application logs pointing at the caller. Here the JVM never reaches `main()`: there is no application log entry at all, only the process's own stderr and exit code. In containerised deployments where stderr goes somewhere nobody reads, the visible symptom is — again — a restart loop with empty logs. That is exactly why this belongs in a startup-script audit rather than being left for an APM tool to catch.

---

## Detect

```bash
grep -rE "java\.security\.manager" \
  deploy/ docker/ k8s/ *.sh *.conf
```

Look beyond your own scripts: application server launch configurations (WebLogic, WebSphere, and Tomcat setups of a certain age), RMI service wrappers, and vendor-supplied start scripts are the classic carriers. The flag is often accompanied by a `-Djava.security.policy=...` pointing at a policy file — that file is dead weight too, and its presence in a repository is a reliable indicator that the manager flag exists somewhere nearby.

---

## Fix

Remove the flag. There is no replacement — the Security Manager is gone, and JEP 486 is explicit that no substitute mechanism is planned inside the JDK. What the Security Manager was *doing* for you needs an answer at a different layer: OS-level sandboxing, container security policies and seccomp profiles, or application-level authorisation.

Be aware that removing the flag can change behaviour beyond startup: code paths that used to be *blocked* by the Security Manager now silently succeed, which is a security posture change, not just a compatibility one. Chapter 3.16 covers that silent side of the same removal — it is the more dangerous half.

---

## Worked example

From [`examples/02-security-manager-startup-flag`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/02-security-manager-startup-flag), verified on Temurin 8u502 and Temurin 25.0.4:

```
JDK 8 with -Djava.security.manager -version:
  openjdk version "1.8.0_502"
  ...
  exit=0

JDK 25 with -Djava.security.manager -version:
  Error occurred during initialization of VM
  java.lang.Error: A command line option has attempted to allow or enable the
  Security Manager. Enabling a Security Manager is not supported.
  	at java.lang.System.initPhase3(java.base@25.0.4/System.java:1970)
  exit=1
```

Note the stack frame: `System.initPhase3` — VM initialisation, not application code. Nothing you wrote appears in this failure, because nothing you wrote ever ran.
