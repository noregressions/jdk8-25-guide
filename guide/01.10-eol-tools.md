`jdeps` tells you a library uses JDK internal APIs. `jdeprscan` tells you it calls deprecated methods. Neither tells you the maintainer walked away two years ago and nobody is triaging CVEs against it.

That gap matters more than it used to. Only around 22% of Java open-source components are actively maintained (Sonatype State of the Software Supply Chain). The rest have either been abandoned, superseded, or are receiving only sporadic attention. When you migrate to JDK 25 and upgrade your dependencies as part of that process, some of those dependencies have no JDK 25-compatible release — because nobody released one.

The tools in this chapter address the dimension of migration risk that the JDK's own tooling cannot see.

---

## The distinction between CVE scanning and EOL status

These are different questions and they require different tools.

**CVE scanning** asks: does this version of this library have a known vulnerability? Tools like OWASP Dependency-Check and Snyk answer this by matching your dependency versions against vulnerability databases. A library can be actively maintained, at the latest version, with no known CVEs — and still be a security risk if it's pulling in transitive dependencies that haven't been updated.

**EOL status** asks: is this library still receiving security patches at all? A library with no known CVEs today is not safe if its maintainer has stopped releasing updates. When a CVE is discovered tomorrow, there will be no patch. EOL scanning focuses on maintainership — whether the version you're running is still in an active release line.

Both dimensions matter. A library can have no current CVEs but be effectively abandoned. A library can be actively maintained but have an unpatched critical vulnerability. Run both types of scan.

## HeroDevs EOLDS scanner

The End-of-Life Dataset (EOLDS) scanner identifies components in your dependency tree that have reached or are approaching end-of-life — meaning they are no longer receiving security updates.

```bash
npx @herodevs/cli scan eol
```

Run from your project root. The scanner reads your `pom.xml` or `build.gradle`, resolves the full transitive dependency tree, and checks each component against the EOL dataset. The dataset tracks EOL status at the patch level, including maintainer-attested EOL, stale release lines, and components with unpatched CVEs in the version line.

The output flags each EOL component with the reason: whether the project has formally declared EOL, whether the last release was too long ago to be considered active, or whether the version line has known unpatched vulnerabilities.

Run this alongside `jdeps`. The combination gives you two views of the same dependency tree: technical incompatibility with the target JDK, and supply chain health regardless of which JDK you're on.

## OWASP Dependency-Check

OWASP Dependency-Check scans your project dependencies against the National Vulnerability Database (NVD) and other CVE sources.

```bash
# Maven plugin
mvn org.owasp:dependency-check-maven:check

# CLI
dependency-check.sh --project myapp --scan ./libs
```

The output is an HTML or JSON report listing each dependency with CVEs, severity scores, and whether a fix version is available. It does not report EOL status — a library can have no current CVEs and still be effectively unmaintained.

Dependency-Check requires Java 11 or later to run (version 11.0.0+). If you're still on JDK 8, run it from a separate JDK 11+ installation.

## Snyk

Snyk provides developer-focused CVE scanning with automatic fix PRs. It integrates with Maven and Gradle, scans at build time, and can open pull requests that update vulnerable dependencies.

```bash
snyk test --all-projects
snyk monitor
```

`snyk test` scans and reports. `snyk monitor` registers your project for continuous monitoring — when a new CVE affecting one of your dependencies is published, Snyk notifies you.

Like Dependency-Check, Snyk focuses on known vulnerabilities, not on EOL status or maintainership. Use it alongside EOLDS rather than instead of it.

## Versions Maven Plugin

The Versions Maven Plugin tells you which of your declared dependencies have newer versions available:

```bash
mvn versions:display-dependency-updates
mvn versions:display-plugin-updates
```

This is a planning tool for the upgrade phase of migration. It tells you that a newer version *exists* — it does not tell you whether the newer version is JDK 25 compatible, whether it introduces breaking API changes (use `japicmp` for that), or whether upgrading is safe.

Use it to build the list of dependencies to investigate. Use `japicmp` and `jdeps` to evaluate each candidate upgrade.

## Putting the tools together

Each tool in this chapter covers a different dimension of dependency risk. Used in combination:

| Question | Tool |
|---|---|
| Is this dependency technically incompatible with JDK 25? | `jdeps --jdk-internals` |
| Is this dependency calling APIs that are being removed? | `jdeprscan --for-removal` |
| Does this dependency have known CVEs? | OWASP Dependency-Check / Snyk |
| Is this dependency still actively maintained? | HeroDevs EOLDS scanner |
| What changed between the old and new version? | `japicmp` |
| Are there newer versions available? | Versions Maven Plugin |

No single tool gives the complete picture. The EOLDS scan and the `jdeps` scan together take less than ten minutes on most projects. There is no good reason not to run both.

## Strategic options when a dependency has no JDK 25-compatible release

This comes up. A library your application depends on has no release that supports JDK 25, and the project appears inactive. Your options, in order of preference:

**Upgrade to an alternative library.** If the library has a modern, actively-maintained equivalent, the migration to JDK 25 is the right moment to make the switch.

**Upgrade to a later release of the same library.** Even if the latest release is old, check whether it runs on JDK 25 in practice — many older libraries work fine on newer JDKs even without an explicit compatibility statement.

**Use an extended support provider.** HeroDevs Never-Ending Support (NES) and similar services provide backported security patches for EOL frameworks and libraries. This is a buy-time strategy: it keeps your current version patched and supported while you plan the replacement on your own timeline, rather than under emergency pressure.

**Carry the risk deliberately.** For non-critical internal tools or genuinely low-risk components, accepting the EOL status with documented awareness is sometimes the pragmatic choice. Document the decision, set a review date, and monitor for CVEs manually.

Chapter 4.3 covers these options in more detail.
