```
Exception in thread "main" java.lang.UnsupportedOperationException
    at java.base/java.lang.Thread.stop(Thread.java:1557)
```

`Thread.stop()` has been deprecated since Java 1.2 — 1998 — for a sound reason: it releases every monitor the victim thread holds as it dies, leaving whatever those locks protected in an arbitrary, corrupted state. What kept it alive in codebases is that for twenty-two years the deprecation had no teeth: the method worked, shipping code used it, and "deprecated" quietly recalibrated in developers' heads to mean "frowned upon but fine."

JDK 20 ended that. The methods still exist on JDK 20–25 but throw `UnsupportedOperationException` unconditionally.

---

## What happened

The enforcement arrived in stages, and the stages matter for anyone pinning versions. `Thread.stop` was terminally deprecated (`forRemoval=true`) in JDK 18 and degraded to throw in JDK 20 — an implementation change without a dedicated JEP, which is why it is absent from JEP-oriented migration checklists. `Thread.suspend()` and `resume()` were degraded on the same schedule and then **removed from the class in JDK 23**; old bytecode calling them there gets `NoSuchMethodError`. `Thread.stop()` itself followed in **JDK 26** — code calling it no longer compiles, and pre-compiled callers get `NoSuchMethodError` instead of the catchable `UnsupportedOperationException`.

So the failure gets *harder* over time: on JDK 25 (this guide's target) a defensive `catch` around a legacy `stop()` call still works; on 26 the method's absence is a linkage error no catch block sees. If your migration is a stepping-stone strategy, don't let a swallowed `UnsupportedOperationException` on 25 hide a call that becomes a crash on the next LTS.

Note this chapter covers `Thread`'s methods. `ThreadGroup`'s identically-named siblings degraded on a different schedule with a different endpoint — they are Chapter 3.21's subject, and conflating the two produces exactly the wrong version numbers.

## Detect

```bash
jdeprscan --for-removal --class-path 'libs/*' app.jar
grep -rEn "\.stop\(\)|\.suspend\(\)|\.resume\(\)" src/ | grep -iv "executor\|service\|watch"
```

The grep needs the exclusion filter because `stop()` is a common method name; confirm the receiver is a `Thread`. Usual habitats: hand-rolled worker pools predating `ExecutorService`, timeout enforcement ("if it runs too long, stop it"), and test harnesses killing stuck fixtures.

---

## Fix

Cooperative cancellation, in whichever form fits the call site:

- `thread.interrupt()` plus code that honours interruption — checks `Thread.interrupted()` in loops and handles `InterruptedException` at blocking calls.
- A shared `volatile boolean running` flag for tight loops that never block.
- At the structural level, move the threads into an `ExecutorService` and cancel via `shutdown()` / `shutdownNow()` / `Future.cancel(true)` — which is interruption with lifecycle management attached.

There is no drop-in replacement for what `stop()` claimed to do, because what it claimed to do — safely kill an uncooperative thread — was never true. Code whose correctness depends on force-killing threads has a design problem the migration is surfacing, not causing.
