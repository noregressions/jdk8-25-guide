This is the chapter about a breakage that hasn't happened yet — deliberately included because it is the cheapest category in the catalogue to get ahead of, and the JDK is telling you, in plain English on stderr, exactly what to do.

---

## What happened

The Foreign Function & Memory API (final in JDK 22, JEP 454) can call arbitrary native code, which makes it exactly as dangerous as JNI — so its dangerous entry points are "restricted methods" that warn unless the calling module has been granted native access. JDK 24 (JEP 472) brought JNI itself under the same regime, adding the `--illegal-native-access` control (warn by default, `deny` available for previewing the future) so that the two native mechanisms converge on one policy: **native access becomes an explicit grant, per module.**

For a JDK 8 migration the checkpoint is really about your dependencies: Netty's epoll transport, compression libraries, crypto providers, and anything else with a `.so`/`.dll` inside will warn on 25 and break when a future release flips the default. One warning is issued per module on first restricted access, so a quiet log means little on a code path that hasn't run yet — this is a category where static scanning beats waiting for warnings.

---

## Detect

This is what `jnativescan` (JDK 24+, covered in Chapter 1.3) exists for:

```bash
jnativescan --class-path 'libs/*'
```

It inventories every JNI and FFM usage across the tree and prints the exact `--enable-native-access` value to copy. For the runtime view, run the suite with `--illegal-native-access=deny` in CI to preview the future default today, the same simulate-tomorrow pattern as the Unsafe flag in Chapter 3.14.

---

## Fix

Grant access explicitly and deliberately:

```
--enable-native-access=ALL-UNNAMED          # classpath applications
--enable-native-access=io.netty.transport   # named modules, one by one
```

`ALL-UNNAMED` is the pragmatic answer for classpath deployments; named-module grants are the precise one. Either way the flag is documentation as much as configuration — a visible list of which parts of your system talk to native code, which is information worth having had all along. Treat additions to it like `--add-opens` entries (Chapter 1.7's discipline rule): each one deserves to be known, not accumulated.

---

## Worked example

From `discovery-tests/13-native-access-warning`, verified on Temurin 25.0.4. The test downcalls `libc`'s `strlen` via FFM — a JDK-25-only demonstration, since FFM has no JDK 8 side (native access there meant hand-written JNI, with no warning system at all):

```
JDK 25, without --enable-native-access:
  WARNING: A restricted method in java.lang.foreign.Linker has been called
  WARNING: java.lang.foreign.Linker::downcallHandle has been called by Native in an unnamed module (file:...)
  WARNING: Use --enable-native-access=ALL-UNNAMED to avoid a warning for callers in this module
  WARNING: Restricted methods will be blocked in a future release unless native access is enabled
  strlen(hello) = 5
  exit=0

JDK 25, with --enable-native-access=ALL-UNNAMED:
  strlen(hello) = 5
  exit=0
```

One honesty note: the eventual hard error is a forward-looking claim about a release that has not shipped — the test proves the warning path and the grant mechanism, not the future break. The migration action is unchanged either way: run `jnativescan` now, add the flag now, and the future default-flip becomes a non-event.
