| **Level** | Recompilation Surprises |
| **Introduced** | `java.lang.Record`: JDK 16 (JEP 395). `java.lang.IO`: JDK 25 (JEP 512) |
| **Symptom** | `error: reference to IO is ambiguous` on recompilation — wildcard imports only |
| **Detect** | Compile against the target JDK — the error names both candidate classes |

```
UseWildcard.java:5: error: reference to IO is ambiguous
    IO.hello();
    ^
  both class mypkg.IO in mypkg and class java.lang.IO in java.lang match
```

Every Java source file implicitly imports `java.lang.*`. So when the platform adds a class to `java.lang`, every codebase in the world silently gains a new name in scope — and any application that already used that name can find its own class ambiguous on recompile. JDK 16 did it with `Record`; JDK 25 does it again with `IO` (JEP 512's console-I/O convenience class). Same pattern, one cycle apart, and no reason to believe it's the last time.

---

## What happened

The collision is narrower than most write-ups claim, and the precision matters because it determines the size of your audit. A user-defined `IO` class breaks **only when the reference reaches it via a wildcard import from another package** — `import mypkg.*;` puts `mypkg.IO` and the implicitly imported `java.lang.IO` on equal footing, and the compiler refuses to pick. Two other paths still resolve fine: same-package references (the package's own types shadow `java.lang`), and explicit single-type imports (`import mypkg.IO;` — a specific import beats an on-demand one). "Any class named IO breaks" overstates it; "any class named IO that other packages reach through star imports" is the actual audit.

Why this bites real codebases: `IO` and `Record` are exactly the short, generic names large codebases statistically contain — an I/O utility class from 2009, a data-record wrapper from before records existed — and exactly the classes that live in old utility packages consumed via wildcard imports nobody has revisited since the IDE generated them.

Old binaries are untouched; this is compile-time name resolution only.

---

## Detect

Trial-compile on the target JDK — the error is explicit and names both candidates. To scope ahead:

```bash
grep -rln "class IO\b\|class Record\b" src/           # do you have the names?
grep -rn "import .*\.\*;" src/                        # who consumes via wildcards?
```

The intersection is your exposure. While you're there, note which *other* of your short class names shadow current `java.lang` residents — the same audit is reusable next cycle.

---

## Fix

Either end of the ambiguity works:

- **Explicit single-type import** at each affected consumer — minimal diff, keeps the class name.
- **Rename the class** — the durable fix if the name was weak anyway, and OpenRewrite-friendly across a large codebase.

And a habit worth adopting from the incident: prefer explicit imports over wildcards in new code. The compiler treats explicit imports as the stronger claim, which is precisely what insulates them from `java.lang`'s future growth.

---

## Worked example

From `discovery-tests/27-java-lang-io-record-collision`, verified on Temurin 8u502 and Temurin 25.0.4 — one `mypkg.IO` class, referenced three ways, plus the `Record` re-run proving the pattern:

```
JDK 25, wildcard import (import mypkg.*):
  UseWildcard.java:5: error: reference to IO is ambiguous
    both class mypkg.IO in mypkg and class java.lang.IO in java.lang match
  exit=1

JDK 25, explicit single-type import (import mypkg.IO):
  exit=0

JDK 8, wildcard import (java.lang.IO doesn't exist yet — control):
  exit=0

JDK 25, same wildcard pattern with java.lang.Record (JDK 16):
  UseWildcardRecord.java:9: error: reference to Record is ambiguous
  exit=1
```

Four runs: the failure, the two escapes, and the proof it's a recurring pattern rather than an IO-shaped accident.
