Native code has always been a blind spot in Java's security model. JNI calls drop below the JVM's access controls entirely — there are no module boundaries, no encapsulation checks, no safety net. The Foreign Function & Memory API (FFM), introduced in JDK 22, is a safer and more capable replacement, but it carries the same risk profile: explicit permission required.

`jnativescan` was introduced in JDK 24 (alongside JEP 472) to address that blind spot. It scans your classpath and identifies every JAR that makes JNI calls or uses the FFM API — the calls that now require `--enable-native-access` to run without warnings, and that will throw on a future JDK without it.

This is a small, focused tool. It does one thing well.

---

## What it finds

- JNI calls: methods declared `native` that call into platform native libraries
- FFM API usage: calls to restricted methods in `java.lang.foreign` that require `--enable-native-access`
- The specific JAR and class making each call

This gives you a precise inventory of which modules in your classpath need the `--enable-native-access` flag, and at what granularity — module name or `ALL-UNNAMED` for code on the classpath.

---

## What it misses

- JNI libraries loaded dynamically at runtime via `System.loadLibrary()` called from non-native Java code. `jnativescan` can identify the class that *declares* the native method, but if the library itself is loaded conditionally or from an external path, you need to verify it exists at runtime.
- Native access via reflection — a class that calls `MethodHandles.lookup().findNative()` at runtime without declaring a `native` method.
- Security implications of *what* the native code does. `jnativescan` tells you the call exists; it does not audit the native library itself.

---

## Key flags

| Flag | Purpose |
|------|---------|
| `--class-path` | Specifies JARs on the unnamed module classpath to scan. |
| `--module-path` | Specifies the module path to scan. |
| `--release <n>` | Target release version for the scan. |
| `--print-native-access` | Prints the modules or `ALL-UNNAMED` value to pass to `--enable-native-access`. The output is ready to copy directly into your startup flags. |

---

## Worked example

```bash
jnativescan \
  --class-path 'libs/*' \
  --print-native-access
```

Example output:

```
libs/netty-transport-native-epoll-4.1.94.jar:
  io.netty.channel.epoll.Native declares native methods:
    io.netty.channel.epoll.Native::epollCreate()I
    io.netty.channel.epoll.Native::epollWait(IJII)I

libs/lz4-java-1.8.0.jar:
  net.jpountz.lz4.LZ4JNI declares native methods:
    net.jpountz.lz4.LZ4JNI::LZ4_compress_fast(...)

libs/conscrypt-openjdk-uber-2.5.2.jar:
  org.conscrypt.NativeCrypto declares native methods:
    [47 native methods]

--enable-native-access: ALL-UNNAMED
```

Working through this output:

**Netty native transport**
Netty's native epoll transport uses JNI for high-performance I/O on Linux. This is expected and intentional — if you're using `netty-transport-native-epoll` you already knew about the native dependency. Add `--enable-native-access=ALL-UNNAMED` (or the specific module if you're on the module path) to your startup flags.

**lz4-java**
The LZ4 compression library uses JNI for its native codec. A pure-Java fallback exists; you can avoid the native call entirely by switching to the Java implementation if the native access flag is a concern.

**conscrypt**
The Conscrypt TLS library is heavily JNI-dependent — 47 native methods is a large surface. If your application uses Conscrypt as its TLS provider, this is a significant native dependency that needs explicit acknowledgement in your startup configuration.

**`--enable-native-access: ALL-UNNAMED`**
The `--print-native-access` flag produces the exact flag value to add to your JVM startup. Since all these JARs are on the unnamed module classpath, the value is `ALL-UNNAMED`. If you run on the named module path, the output lists specific module names.

---

## Why this matters now

On JDK 25, native access without `--enable-native-access` produces a warning to stderr on the first restricted operation from each module. Warnings are tolerable — they pollute logs and signal technical debt, but they don't break anything.

That changes. The JDK has been moving steadily toward making unauthorised native access a hard error. When that happens, any application that hasn't added `--enable-native-access` will fail at the point of the first native call.

Run `jnativescan` now and add the flag. The flag itself is cheap to add; scrambling to find which library is making native calls when your application starts throwing is not.
