| **Level** | Runs But Wrong |
| **Introduced** | JDK 25 (JEP 519 — product option, **default OFF**) |
| **Symptom** | Garbage data, heap corruption, delayed crashes — *only when `-XX:+UseCompactObjectHeaders` is enabled* |
| **Detect** | Run the test suite with the flag on plus `--sun-misc-unsafe-memory-access=debug`; search for `objectFieldOffset` |

First, the fact this chapter hinges on, verified directly because published material — including earlier versions of this guide's own deck — keeps getting it wrong:

```
JDK 25 -XX:+PrintFlagsFinal | grep UseCompactObjectHeaders:
  bool UseCompactObjectHeaders = false {product lp64_product} {default}
```

Compact object headers shipped in JDK 25 as a **product option, off by default**. This is not a day-one migration risk. It is a day-*two* risk with a specific trigger — someone enabling the flag for its very real benefits — and a failure mode nasty enough to earn its chapter before that happens.

---

## What happened

JEP 519 shrinks the object header from 128 to 64 bits, cutting per-object overhead and shrinking heaps for small-object-heavy workloads. Every field in every object moves.

That is harmless to any code using the language: field access compiles to names, and the JVM resolves layout at runtime. It is fatal to a specific pattern from the `sun.misc.Unsafe` world (Chapter 3.14): call `Unsafe.objectFieldOffset()` once, cache the numeric result in a `static final`, and use it for raw reads and CAS operations ever after — a standard performance idiom in older concurrency and serialisation libraries. A cached offset computed under one header layout is simply a wrong number under the other. With the flag on, reads through it return garbage, writes corrupt adjacent memory, and the visible symptom — wrong data, an impossible value, a crash three subsystems away — appears nowhere near the cause.

Being wrong *by a constant* rather than throwing is what elevates this over most Unsafe hazards: nothing fails at the offending line, ever.

The reason to act now: the applications most likely to carry cached-offset code — old high-performance libraries — are exactly the applications whose heap profiles make the flag most tempting to ops teams. The trigger is a config change anyone can make, not a JDK release.

---

## Detect

```bash
grep -rn "objectFieldOffset" src/            # plus your dependency sources
java -XX:+UseCompactObjectHeaders --sun-misc-unsafe-memory-access=debug -jar app.jar
```

The combined run is the real detector: the flag creates the condition, and `debug` mode stack-traces every Unsafe memory access so you can match each against the new layout. Run the full test suite that way once, before anyone enables the flag in production for the heap savings.

---

## Fix

Migrate cached-offset code to `VarHandle`, which resolves fields symbolically and is correct under any layout the JVM chooses — this is the same migration Chapter 3.14 already requires for the Unsafe eviction, and this chapter is the reason "the warnings still work" isn't a reason to defer it. For dependencies, the usual rule: current versions of the major performance libraries have already moved; the risk concentrates in old pins and the unmaintained tail.

Until the audit is done, the operational rule is simpler: treat `-XX:+UseCompactObjectHeaders` as a change that requires the Unsafe audit to have happened, not as a free heap discount.

## Worked example

From [`examples/20-compact-object-headers-default`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/20-compact-object-headers-default), verified on Temurin 25.0.4 — a JDK-25-only check, since the flag doesn't exist earlier:

```
JDK 25 -XX:+PrintFlagsFinal | grep UseCompactObjectHeaders:
  bool UseCompactObjectHeaders = false {product lp64_product} {default}
shipped default value: false
```

Deliberately narrow: it verifies the shipped default, because that is the load-bearing fact this category's public coverage keeps misstating. The corruption scenario itself — a cached offset reused across a layout change — is real but timing-sensitive, and is exactly what the combined detect run above exists to surface in *your* code rather than in a synthetic demo.
