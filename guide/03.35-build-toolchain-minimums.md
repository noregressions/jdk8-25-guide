| **Level** | Environment, Distribution & Build Toolchain |
| **Introduced** | N/A — not a JDK change but a compatibility-matrix problem across the build ecosystem |
| **Symptom** | Compiler plugins, Surefire, Gradle, Kotlin/Groovy/Scala compilers, and ASM-based plugins (JaCoCo, Mockito's engine) fail against JDK 25 class files independently of your code |
| **Detect** | Check each tool's JDK 25 support matrix before cutting the migration branch |

```
Old ASM (7.3.1) parsing a JDK-25-compiled class file:
  java.lang.IllegalArgumentException: Unsupported class file major version 69
      at org.objectweb.asm.ClassReader.<init>(ClassReader.java:196)
```

Your build is a stack of software with its own JDK opinions, and most of it reads bytecode: coverage instrumentation, mocking engines, Gradle's own internals, every compiler that isn't `javac`. Chapter 3.12 covered this mechanism striking at runtime; this chapter is the build-time face of the same class-file-version arithmetic — and it deserves separate billing because it fails *first*, before a single test of your actual application runs.

---

## What happened

Nothing, in the JDK — which is the point of the "N/A" above. Class file version 69 is just JDK 25 doing what every release does. What changes is the required floor across your build's dependency stack, and the failure wears the tool's clothing rather than the JVM's: as the verified run shows, old ASM wraps the rejection in its own `IllegalArgumentException` whose message never says "your JDK is newer than your JaCoCo" — it says a class file is unsupported, deep inside a plugin stack trace. Triaging that without knowing this chapter costs an afternoon; with it, the message *is* the diagnosis.

The practical floors move with every JDK release, so treat any published table as a checking prompt rather than gospel: current Maven compiler/Surefire plugins, Gradle with explicit JDK 25 support, ASM 9.8+, ByteBuddy 1.17.5+, Mockito 5.x, current JaCoCo — and for mixed-language builds, Kotlin/Groovy/Scala compiler versions with declared JDK 25 support, each verified against its own release notes.

---

## Detect

Before the migration branch exists: walk each build plugin's documentation for its JDK 25 statement. Empirically, the cheap smoke test is a toolchain-only dry run — current build tools compile *for* an older target while running *on* a new JDK, so you can prove the toolchain on JDK 25 while still shipping JDK 8 bytecode:

```bash
mvn -T1C clean verify -DskipTests    # on JDK 25, before changing --release
mvn clean verify                      # then with tests: Surefire + agents get their vote
```

Anything that breaks in those runs is toolchain, by construction — your code hasn't changed.

---

## Fix

Upgrade the toolchain **first**, as its own separate, low-risk step — shippable while the application still targets JDK 8, reviewable as pure infrastructure, and reversible. This is the playbook's ordering rule (Chapter 5.1), and this chapter is the evidence for it: every failure in this category is indistinguishable from migration chaos when bundled into the JDK switch, and trivially attributable when done a week earlier.

## Worked example

From [`examples/35-build-toolchain-asm-version`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/35-build-toolchain-asm-version), verified on Temurin 25.0.4 with real ASM jars from Maven Central — the exact library JaCoCo, Mockito, and countless Gradle/Maven plugins embed:

```
Old ASM (7.3.1) parsing a JDK-25-compiled class file:
  Exception in thread "main" java.lang.IllegalArgumentException: Unsupported class file major version 69
      at org.objectweb.asm.ClassReader.<init>(ClassReader.java:196)

New ASM (9.8) parsing the SAME class file:
  parsed class: Target
```

One version bump between an opaque plugin crash and a working build — multiplied by however many bytecode readers your toolchain contains.
