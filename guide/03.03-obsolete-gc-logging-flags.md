| | |
|---|---|
| **Level** | Won't Start (partially — see below) |
| **Introduced** | JDK 9 unified logging (JEP 158, JEP 271) |
| **Symptom** | Mixed: `-XX:+PrintGCTimeStamps` and most of the `PrintGC*` family are startup-fatal; `-XX:+PrintGCDetails` and `-verbose:gc` survive as deprecated aliases |
| **Detect** | Audit startup scripts for `-XX:+PrintGC*`; trial-run each *specific* flag against the target JDK |

Your monitoring configuration can stop your application from starting. A typical JDK 8 GC logging line looks like this:

```
-verbose:gc -XX:+PrintGCDetails -XX:+PrintGCTimeStamps
```

On JDK 25, one of those three flags kills the JVM:

```
Unrecognized VM option 'PrintGCTimeStamps'
Error: Could not create the Java Virtual Machine.
```

The trap in this category is that the flags *sound* like siblings and are usually documented in a single breath — but they did not all go the same way, and a category-level claim ("the `PrintGC*` family is fatal") will mislead you in both directions.

---

## What happened

JDK 9 replaced the accumulated, ad-hoc GC logging flags with the unified logging framework (`-Xlog`, JEP 158; GC logging specifically, JEP 271). What is easy to miss is that the old flags were then treated in two different ways:

- **Kept as deprecated aliases.** `-verbose:gc` and `-XX:+PrintGCDetails` still work on JDK 25. Each prints a deprecation warning and translates itself into the unified equivalent (`-Xlog:gc` and `-Xlog:gc*` respectively). Startup proceeds.
- **Removed outright.** `-XX:+PrintGCTimeStamps`, and most of the rest of the `PrintGC*` family, are unrecognised options — startup-fatal, exactly like the obsolete collector flags in Chapter 3.1.

So whether your configuration starts at all depends on *which specific flags* it carries — test each one, not the category. And note the second-order trap: even where the alias survives, it emits output in the **new unified-logging format**. A JDK 8-era log parser, alerting rule, or scraping script keyed to the old text format breaks either way. Surviving startup is not the same as surviving migration.

---

## Detect

```bash
grep -rE "verbose:gc|PrintGC|Xloggc" deploy/ docker/ k8s/ *.sh
```

Then trial-run each hit individually against the target JDK — `java <flag> -version` answers per-flag in seconds. Don't assume: the fatal/harmless line runs through the middle of what looks like one family.

---

## Fix

Migrate to unified logging regardless of which old flags currently "work" — the aliases are deprecated, and their output format has already changed under you. The workhorse replacement line is:

```
-Xlog:gc*:file=gc.log:time,uptime,level,tags
```

The common conversions:

| JDK 8 flag | JDK 9+ equivalent |
|---|---|
| `-verbose:gc` | `-Xlog:gc` |
| `-XX:+PrintGCDetails` | `-Xlog:gc*` |
| `-XX:+PrintGCTimeStamps` | the `time`/`uptime` decorators: `-Xlog:gc*::time,uptime` |

Budget for updating whatever consumes the logs at the same time — the structure, decorations, and line shapes are all different in unified logging, so parsers and dashboards need reworking alongside the flags.

---

## Worked example

From `discovery-tests/03-obsolete-gc-logging-flags`, verified on Temurin 8u502 and Temurin 25.0.4 — three flags, three different outcomes:

```
-XX:+PrintGCDetails:
  JDK8  -XX:+PrintGCDetails -> exit=0
    openjdk version "1.8.0_502"
  JDK25 -XX:+PrintGCDetails -> exit=0
    [0.001s][warning][gc] -XX:+PrintGCDetails is deprecated. Will use -Xlog:gc* instead.

-XX:+PrintGCTimeStamps:
  JDK8  -XX:+PrintGCTimeStamps -> exit=0
    openjdk version "1.8.0_502"
  JDK25 -XX:+PrintGCTimeStamps -> exit=1
    Unrecognized VM option 'PrintGCTimeStamps'

-verbose:gc:
  JDK8  -verbose:gc -> exit=0
  JDK25 -verbose:gc -> exit=0
    [0.005s][info][gc] Using G1
```

`PrintGCDetails` survives with a warning; `PrintGCTimeStamps` refuses to start; `-verbose:gc` works and is already speaking the new format (`[0.005s][info][gc]` — those decorations are unified logging, not the JDK 8 output shape). One configuration line, three behaviours.
