The tools in the previous chapters find problems. OpenRewrite fixes them — automatically, across your entire codebase, in a single command.

The key distinction from search-and-replace is that OpenRewrite works on the Abstract Syntax Tree (AST). It understands Java source code semantically: it knows the difference between a `javax.annotation.PostConstruct` import and a local variable named `PostConstruct`, and it only changes the one that needs changing. It preserves your formatting, your comments, and your code style. The resulting diff is surgical.

For migration work, the practical use is straightforward: pick the recipe that matches your migration target, run it, review the diff, commit. You do not need to understand the internals.

---

## What OpenRewrite automates

The most useful recipes for a JDK 8 to 25 migration:

| Recipe | What it does |
|---|---|
| `JavaxMigrationToJakarta` | Renames `javax.*` imports to `jakarta.*`, updates Maven dependencies, and handles XML namespace changes |
| `JakartaEE10` | Full Jakarta EE 10 migration — includes `JavaxMigrationToJakarta` |
| `Java8toJava11` | JDK 8 to 11 API migration |
| `UpgradeToJava17` | JDK 11 to 17 migration |
| `UpgradeToJava21` | JDK 17 to 21 migration |
| `UpgradeToJava25` | JDK 21 to 25 migration (rewrite-migrate-java 3.30.0+) |
| `SpringBoot3BestPractices` | Spring Boot 2.x to 3.x — includes Jakarta migration |
| `JUnit5BestPractices` | JUnit 4 to JUnit 5 |

Recipes compose. `JavaxMigrationToJakarta` is included inside `JakartaEE10`, which is included inside `SpringBoot3BestPractices`. Pick the highest-level recipe that covers your migration target. Running multiple overlapping recipes is harmless but redundant.

---

## What OpenRewrite does not fix

OpenRewrite handles syntactic and import-level changes. It cannot fix:

- Runtime-only failures — `InaccessibleObjectException`, `NoClassDefFoundError`, behavioural changes
- Binary-only third-party JARs — it needs source code to transform
- Behavioural changes: charset defaults, locale data, GC behaviour, Security Manager paths
- Dependency compatibility — it will update the import but cannot guarantee the upgraded library version compiles

The tools in Chapters 1.1 to 1.8 identify these categories. OpenRewrite handles the mechanical source changes after you've assessed the broader problem.

## Running a recipe

OpenRewrite can run against your project without modifying your `pom.xml`. The Maven plugin accepts recipe coordinates on the command line:

```bash
mvn -U org.openrewrite.maven:rewrite-maven-plugin:run \
  -Drewrite.recipeArtifactCoordinates=\
    org.openrewrite.recipe:rewrite-migrate-java:RELEASE \
  -Drewrite.activeRecipes=\
    org.openrewrite.java.migrate.jakarta.JavaxMigrationToJakarta
```

For the Jakarta + Spring Boot 3 migration (which is the most common combined migration):

```bash
mvn -U org.openrewrite.maven:rewrite-maven-plugin:run \
  -Drewrite.recipeArtifactCoordinates=\
    org.openrewrite.recipe:rewrite-spring:RELEASE \
  -Drewrite.activeRecipes=\
    org.openrewrite.java.spring.boot3.SpringBoot3BestPractices
```

Review the resulting diff with your normal code review process before committing. OpenRewrite's changes are correct but your test suite is the confirmation.

## The Lombok trap

One specific pitfall worth calling out. Since JDK 23, `javac` no longer runs annotation processors by default unless explicitly configured (JDK-8321319 — a javac release-note change; there is no JEP for it). Lombok relies on annotation processing to generate getters, setters, builders, and constructors at compile time.

After a migration to JDK 23 or later, the generated methods are absent. A direct caller of `user.getName()` fails to compile with `cannot find symbol` — noisy, but easy to diagnose. The dangerous shape is the reflective or framework-style caller (Jackson, Spring, JPA): the build succeeds with no errors, and the missing method surfaces only at runtime as `NoSuchMethodError` or its reflective equivalent.

The fix has two parts. First, update Lombok to version 1.18.40 or later, which added JDK 25 support (in practice, use 1.18.44 or later — subsequent releases fixed JDK 25 bugs). Second, explicitly configure the annotation processor in your build:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <annotationProcessorPaths>
      <path>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.44</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>
```
