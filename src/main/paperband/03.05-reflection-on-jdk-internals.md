The most common runtime crash in a JDK 8 migration looks like this:

```
Exception in thread "main" java.lang.reflect.InaccessibleObjectException: Unable to make
field private final byte[] java.lang.String.value accessible: module java.base does not
"opens java.lang" to unnamed module @2b2fa4f7
```

The pattern that triggers it — `getDeclaredField(...)` on a JDK class followed by `setAccessible(true)` — was routine for a decade. Serialisation libraries, dependency-injection containers, and mocking frameworks of the JDK 8 era all reached into JDK internals this way, deliberately and successfully. Old Spring, Hibernate, Gson, and Jackson versions did it as a matter of course. Which is the point: **the call is almost never in your code.** It is in a dependency, pinned at whatever version was current when the application was written.

---

## What happened

The module system (JDK 9) gave the JDK the means to enforce its own boundaries, but enforcement arrived gradually. JDK 9 through 15 permitted illegal reflective access by default and merely warned. JDK 16 flipped the default to deny (JEP 396). JDK 17 removed the `--illegal-access` escape hatch entirely (JEP 403), leaving only targeted, per-package grants via `--add-opens`. Nothing about your class files changes — the same bytecode that ran cleanly on JDK 8 throws on JDK 25 because the *JVM's* rules changed, not yours.

Note the exception's precision: it names the field, the owning module, the missing `opens`, and the requesting module. That message is a ready-made fix instruction — but only if you ever see it. Frameworks frequently catch reflection failures and fall back to slower paths or degraded behaviour silently, which converts this crash category into a performance or correctness mystery. That is exactly what `-Xlog:exceptions=info` exists to surface.

---

## Detect

Run `jdeps --jdk-internals` across your full dependency tree (Chapter 1.1) — it names each internal API and, for the well-known offenders, its standard replacement. But remember what static analysis misses: reflection assembled at runtime, `Class.forName` with computed names, and anything behind a framework abstraction. Complement it with a runtime pass:

```bash
java -Xlog:exceptions=info -jar app.jar 2>&1 | grep InaccessibleObjectException
```

on a workload that exercises the real code paths. The log shows every thrown instance — including the ones a framework catches before they reach you.

---

## Fix

In preference order:

1. **Upgrade the dependency.** Every mainstream framework fixed its internal-access patterns years ago; the version of Spring, Hibernate, Gson, or Jackson that fails is a version with known CVEs anyway. This is the real fix.
2. **Targeted `--add-opens`** for the cases an upgrade can't reach yet:

   ```
   --add-opens java.base/java.lang=ALL-UNNAMED
   ```

   Every such flag is a debt marker, not a solution. Apply the discipline rule from Chapter 1.7: each one gets a tracking issue, an owner, and a removal date. The target state is zero.

What is *not* a fix: `--illegal-access=permit`. It was removed in JDK 17 and is itself an unrecognised-option risk.

## Worked example

From [`examples/05-reflection-on-jdk-internals`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/05-reflection-on-jdk-internals), verified 2026-08-07 on Temurin 8u502 and Temurin 25.0.4. The test class does exactly what old serialisation frameworks did — reach `String`'s private `value` field:

```java
Field f = String.class.getDeclaredField("value");
f.setAccessible(true);
```

```
$ java8 Reflect
Access succeeded, field type: class [C
exit=0

$ java25 Reflect
Exception in thread "main" java.lang.reflect.InaccessibleObjectException: Unable to make
field private final byte[] java.lang.String.value accessible: module java.base does not
"opens java.lang" to unnamed module @2b2fa4f7
exit=1
```

Same source, same class file — a runtime enforcement change. Two details worth noticing: the field *type* differs between the runs (`[C` — a char array — on JDK 8; the exception names `byte[]` on 25, courtesy of compact strings in JDK 9), a reminder that code depending on internals was never protected from the internals changing underneath it. And re-running with `--add-opens java.base/java.lang=ALL-UNNAMED` restores the JDK 8 behaviour — the escape hatch works, and should still be treated as temporary.
