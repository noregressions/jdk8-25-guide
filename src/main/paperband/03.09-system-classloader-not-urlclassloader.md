| **Level** | Crashes at Runtime |
| **Introduced** | JDK 9 (JEP 261 — Module System; the application classloader now extends `BuiltinClassLoader`) |
| **Symptom** | `ClassCastException: ... ClassLoaders$AppClassLoader cannot be cast to class java.net.URLClassLoader` |
| **Detect** | Search for `(URLClassLoader)` casts on `getSystemClassLoader()` / `getContextClassLoader()` |

```
Exception in thread "main" java.lang.ClassCastException: class
jdk.internal.loader.ClassLoaders$AppClassLoader cannot be cast to class
java.net.URLClassLoader
```

On JDK 8 the system classloader happened to be a `java.net.URLClassLoader`, and an ecosystem of hacks grew on that accident: cast it, call `getURLs()` to enumerate the classpath, or reflect into `addURL()` to inject JARs at runtime. Classpath scanners, plugin loaders, self-updating applications, and uncounted Stack Overflow answers all did it. None of it was ever contractual — `getSystemClassLoader()` promises a `ClassLoader`, nothing more — and JDK 9 called the bluff.

---

## What happened

The module system (JEP 261) reimplemented the built-in classloaders; the application classloader is now `jdk.internal.loader.ClassLoaders$AppClassLoader`, which does not extend `URLClassLoader`. The cast fails on JDK 9 and every release since. This is one of the most common real-world JDK 9+ failures despite never making most conference-talk lists, because it lives in infrastructure code — the kind that was written once in 2012 and works until the day it doesn't.

The failure is at least honest: a `ClassCastException` at the cast site, naming both classes. What is less honest is *where* it surfaces — frequently inside a third-party library's classpath-scanning routine during startup, presenting as a framework bootstrap failure rather than an application bug.

---

## Detect

```bash
grep -rE "\(URLClassLoader\)|URLClassLoader\.class\.cast|addURL" src/
```

Include dependencies in the sweep if you can get sources; classpath-scanning libraries pinned at JDK 8-era versions are the usual indirect carriers, and the fix there is a version bump rather than code surgery.

---

## Fix

Pick the replacement that matches what the cast was *for*:

- **Enumerating the classpath** → read the `java.class.path` system property and split on `File.pathSeparator`. That is what `getURLs()` was being used to approximate.
- **Discovering implementations** → `ServiceLoader`, which is the supported answer to "find the plugins" and works identically on classpath and module path.
- **Loading JARs at runtime** → construct your own child loader: `new URLClassLoader(urls, getClass().getClassLoader())` and load through it. Creating a `URLClassLoader` is still fully supported — what changed is only that the *system* loader isn't one.

The third option changes visibility semantics slightly (classes load in a child, not the application loader), which is almost always acceptable and occasionally exactly the isolation the original hack was fighting against.

---

## Worked example

From [`examples/09-system-classloader-not-urlclassloader`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/09-system-classloader-not-urlclassloader), verified on Temurin 8u502 and Temurin 25.0.4:

```java
ClassLoader cl = ClassLoader.getSystemClassLoader();
URLClassLoader ucl = (URLClassLoader) cl;   // the JDK 8-era hack
```

```
JDK 8:
  classloader = sun.misc.Launcher$AppClassLoader
  cast ok: sun.misc.Launcher$AppClassLoader@4e0e2f2a
  exit=0

JDK 25:
  classloader = jdk.internal.loader.ClassLoaders$AppClassLoader
  Exception in thread "main" java.lang.ClassCastException: class
  jdk.internal.loader.ClassLoaders$AppClassLoader cannot be cast to class
  java.net.URLClassLoader (jdk.internal.loader.ClassLoaders$AppClassLoader and
  java.net.URLClassLoader are in module java.base of loader 'bootstrap')
  exit=1
```

Note the loader class names on the two JDKs — `sun.misc.Launcher$AppClassLoader` versus `jdk.internal.loader.ClassLoaders$AppClassLoader`. Code that string-matched on the JDK 8 name (another period habit) breaks on the same line for a different reason.
