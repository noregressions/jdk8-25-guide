```
javac8-compiled class:  StringBuilder instructions: 15 occurrences
javac25-compiled class: invokedynamic instructions:  2 occurrences
```

Since JDK 9, `javac` compiles `a + b + c` not to a chain of `StringBuilder.append()` calls but to a single `invokedynamic` call site, letting the JVM choose the assembly strategy at runtime (JEP 280). Faster, less garbage, dramatically smaller bytecode for concat-heavy code. That much is real, `javap`-visible, and worth knowing.

This chapter also exists to kill a claim. Migration write-ups — including earlier versions of this project's own material — assert that the change can reorder side-effecting `toString()` calls on recompiled code. **It cannot, and it does not.**

---

## What happened — and what didn't

The Java Language Specification pins the operands of `+` to strict left-to-right evaluation, and that rule sits *above* whatever bytecode the compiler emits. The `invokedynamic` strategy still pushes each operand's value onto the stack in source order before the call site fires; JEP 280 changed how the JVM *assembles the final string*, not when each piece is computed. There is no compiler-legal way for the strategy switch to reorder side effects on any JDK.

The claim was tested twice, independently, before being struck from this guide: once with the `char[]`-concatenation example that circulates in write-ups (which turns out to demonstrate an unrelated, version-independent gotcha — `Object.toString()` on arrays — not an ordering change), and once with a purpose-built construction of three side-effecting `toString()` objects, compiled by both compilers, run three ways including old-bytecode-on-new-JVM. Identical call order, every time. The myth likely survives because the *bytecode* visibly changes, and a visible change invites behavioural suspicion.

What *is* affected by the real change: anyone reading `javap` output (the disassembly looks completely different), and bytecode-manipulation tooling, which now meets `invokedynamic` call sites where it expected `StringBuilder` patterns — Chapter 3.12's category, and the practical reason this chapter matters beyond myth-hygiene.

---

## Detect

Nothing to detect for correctness. For tooling and disassembly-readers:

```bash
javap -c MyClass.class | grep -cE "StringBuilder|makeConcatWithConstants"
```

on artefacts from each compiler shows which world each class file lives in. (`javac --release 8` on JDK 25 still emits the old `StringBuilder` shape — relevant if a bytecode tool downstream can't yet parse the new one.)

---

## Fix

Nothing to fix. Resist "fixing" it: rewriting `+` into manual `StringBuilder` chains to recreate the old bytecode forfeits JEP 280's optimisation and defends against a problem that testing shows does not exist.

## Worked example

From [`examples/28-string-concat-bytecode-strategy`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/28-string-concat-bytecode-strategy), verified on Temurin 8u502 and Temurin 25.0.4 — three objects with side-effecting `toString()` methods, concatenated; compiled by `javac8` and `javac25`; run three ways:

```
javac8-compiled, run on JDK 8:
  toString() call #1 on Loud#1
  toString() call #2 on Loud#2
  toString() call #3 on Loud#3
  result = [L1,L2,L3]

javac25-compiled, run on JDK 25:            identical order
javac8-compiled, run on JDK 25 (no recompile): identical order

Bytecode strategy comparison (javap -c):
  javac8-compiled:  StringBuilder instructions — 15 occurrence(s)
  javac25-compiled: invokedynamic instructions — 2 occurrence(s)
```

Same observable behaviour across every combination; genuinely different bytecode. Both facts in one test — which is the standard every claim in this level is held to.
