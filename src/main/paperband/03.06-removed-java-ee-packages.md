| | |
|---|---|
| **Level** | Crashes at Runtime |
| **Introduced** | JDK 11 (JEP 320) |
| **Symptom** | `NoClassDefFoundError` / `ClassNotFoundException` for `javax.xml.bind.*`, `javax.annotation.*`, `javax.activation.*`, `javax.xml.ws.*`, `javax.transaction.*`, CORBA |
| **Detect** | `jdeprscan --for-removal` on JDK 8 output (Chapter 1.2); or simply compile against JDK 11+ |

```
Exception in thread "main" java.lang.NoClassDefFoundError: javax/xml/bind/annotation/XmlRootElement
Caused by: java.lang.ClassNotFoundException: javax.xml.bind.annotation.XmlRootElement
```

JAXB is the classic carrier, but this category covers six modules the JDK once bundled and JDK 11 removed outright: JAXB, JAX-WS, the common annotations (`javax.annotation`), JavaBeans Activation, JTA's API classes, and CORBA. The classes were removed, not renamed and not relocated — nothing about the runtime helps you find where they went.

---

## What happened

The Java EE modules were deprecated in JDK 9 and removed in JDK 11 (JEP 320) as part of handing them to Eclipse under the Jakarta banner. An application compiled on JDK 8 carries references to these classes in its bytecode; the same class file that ran for years fails at class-load time on JDK 11+ because the runtime simply no longer ships them.

Three traps make this worse than a straightforward missing dependency:

**It bites code that has nothing to do with XML.** `DatatypeConverter.printBase64Binary()` lived in `javax.xml.bind` and was a popular pre-JDK 8 way to do Base64 — utility code full of it breaks despite never touching JAXB deliberately.

**The replacement has two generations.** The 2017–2020 stopgap artefacts kept the `javax.*` package names; Jakarta EE 9+ moved everything to `jakarta.*`. Teams that migrated to JDK 11 once already may be sitting on the Generation 1 artefacts, which are themselves approaching end of life. Migrating today, go straight to `jakarta.*` — the import rename is mechanical, and OpenRewrite automates it (Chapter 1.9).

**JAXB needs two artefacts and quietly implies a third.** The API JAR alone compiles but `JAXBContext.newInstance()` fails without a runtime implementation; and JAXB depends on Activation, whose absence surfaces as a `javax/activation/DataSource` error that never mentions JAXB at all.

One detection nuance that catches even careful teams: `jdeps --jdk-internals` does **not** find these. These were removed *public* APIs, not encapsulated internals — a different mechanism needing a different tool (`jdeprscan` on JDK 8-era output, or the compiler itself on JDK 11+). Don't let a clean internals report stand in for this category.

## Detect

```bash
jdeprscan --for-removal --class-path 'libs/*' app.jar   # run on a JDK that still knows the classes
grep -rE "javax\.(xml\.bind|xml\.ws|annotation|activation|transaction)" src/
```

The cheapest complete detector is a trial compile against the target JDK — every removed reference becomes a compile error with a file and line number.

---

## Fix

Declare the Jakarta replacements explicitly. For the most common case (JAXB — API plus runtime):

```xml
<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>4.0.2</version>
</dependency>
<dependency>
    <groupId>org.glassfish.jaxb</groupId>
    <artifactId>jaxb-runtime</artifactId>
    <version>4.0.5</version>
</dependency>
```

Appendix B carries the full table — all six modules, their removed packages, key classes, and pinned Maven coordinates, including the annotation, activation, JAX-WS, and JTA artefacts. CORBA is the one exception with no replacement: code using it needs redesign, not a dependency. Note the `jakarta.*` generation renames packages in *source*, so calls change from `javax.xml.bind` to `jakarta.xml.bind` imports as part of the same move.

## Worked example

From [`examples/06-removed-java-ee-packages`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/06-removed-java-ee-packages), verified on Temurin 8u502 and Temurin 25.0.4. One class, one reference to `XmlRootElement`, compiled once on JDK 8 — then the **same class file**, no recompile:

```
JDK 8:
  javax.xml.bind.annotation.XmlRootElement
  exit=0

JDK 25 (same .class file, no recompile):
  Exception in thread "main" java.lang.NoClassDefFoundError: javax/xml/bind/annotation/XmlRootElement
      at EE.main(EE.java:4)
  Caused by: java.lang.ClassNotFoundException: javax.xml.bind.annotation.XmlRootElement
      at java.base/jdk.internal.loader.BuiltinClassLoader.loadClass(BuiltinClassLoader.java:580)
  exit=1
```

Nothing about the application changed — only what the runtime bundles.
