Between the static analysis of Chapters 1.1 to 1.5 and the full flight recording of Chapter 1.6, there's a set of JVM flags that occupy useful middle ground: they run during your test suite, require no post-processing, and surface specific categories of migration failure directly to the console.

These flags don't replace JFR. They complement it. Use them during integration testing to catch the issues that are easiest to miss: exceptions that frameworks catch and hide, code that depends on pre-JDK 18 charset behaviour, and `Unsafe` usages in your dependency tree that will break in the next release.

Each flag in this chapter is a diagnostic tool during migration. None of them belong in a production configuration.

---

## `-Xlog:exceptions=info`

Logs every exception the JVM creates — including exceptions that are caught and never printed, and exceptions that frameworks swallow as part of their fallback logic.

```bash
java -Xlog:exceptions=info -jar myapp.jar 2>&1 | \
  grep -i "InaccessibleObject\|IllegalAccess\|NoClassDef\|NoSuchMethod"
```

This is the single most underused migration diagnostic available. The failure mode it targets is specific: a framework tries to call `setAccessible(true)` on a JDK internal field, gets `InaccessibleObjectException`, catches it, and falls back to a different strategy — one that either works less well or fails differently downstream. Without this flag, you see the downstream failure (a `NullPointerException`, a garbled response, an initialisation timeout) and have no idea that the real cause was caught and buried three calls up the stack.

Filter the output for:

| Exception | What it indicates |
|---|---|
| `InaccessibleObjectException` | Reflective access to encapsulated JDK internals — module system enforcement |
| `IllegalAccessException` | Similar — access control violation in reflection |
| `NoClassDefFoundError` | A class expected at runtime is not on the classpath — often removed Java EE packages |
| `NoSuchMethodError` | Binary incompatibility — a method exists in source but not at the compiled signature |
| `UnsupportedOperationException` | Security Manager calls, deprecated Thread methods, or other removed behaviour |

## `--sun-misc-unsafe-memory-access`

Controls the JVM's response to calls to `sun.misc.Unsafe` memory-access methods — the 79 methods that are on the removal path.

```
=warn    Warning on first use per call site (default since JDK 24)
=debug   Full stack trace on every call — use this for migration diagnosis
=deny    Throws UnsupportedOperationException — simulates future JDK behaviour
=allow   Suppresses all warnings — escape hatch only, use with caution
```

During migration, run with `=debug`:

```bash
java --sun-misc-unsafe-memory-access=debug -jar myapp.jar
```

The `=debug` mode gives you the full stack trace for every `Unsafe` memory-access call, not just the first one per call site. This reveals which libraries are using `Unsafe` and precisely where — information you need to assess whether upgrading the library resolves the issue.

Once you've identified and resolved the findings, run with `=deny` in your CI pipeline:

```bash
java --sun-misc-unsafe-memory-access=deny -jar myapp.jar
```

`=deny` causes the JVM to throw instead of warn. If your application starts and its test suite passes under `=deny`, you have confirmed that no code path you exercise depends on `Unsafe` memory-access methods. That is the target state.

## `-Dfile.encoding=COMPAT`

JDK 18 made UTF-8 the default charset on all platforms (JEP 400). Before that, the default was platform-dependent — `windows-1252` on Western European Windows, `Shift_JIS` on Japanese Windows, `UTF-8` on most Linux and macOS systems.

Applications that use `FileReader`, `FileWriter`, `InputStreamReader`, or `OutputStreamWriter` without specifying an explicit charset have an implicit dependency on the platform default. On Windows, this means they were reading and writing files in the platform encoding. After migration to JDK 18 or later, they read and write in UTF-8. Files written before the migration can no longer be read correctly. Data is corrupted without any error.

`-Dfile.encoding=COMPAT` restores the pre-JDK 18 behaviour, using the platform default charset as the default for `FileReader` and `FileWriter`:

```bash
java -Dfile.encoding=COMPAT -jar myapp.jar
```

Use this flag while you locate and fix every `FileReader`, `FileWriter`, `InputStreamReader`, and `OutputStreamWriter` call that lacks an explicit charset argument. The fix is to pass `StandardCharsets.UTF_8` (or the appropriate charset) explicitly. The flag is a workaround that prevents data corruption while the fix is in progress. Chapter 3.18 covers this failure mode in full.

## `-Djava.locale.providers=COMPAT,CLDR`

JDK 9 switched the default locale data source from the JRE's own locale data to the Unicode CLDR dataset (JEP 252). CLDR is more accurate and more broadly maintained, but formatted output changed: dates, currency symbols, number formats, and era names can all differ between the two datasets.

```bash
java -Djava.locale.providers=COMPAT,CLDR -jar myapp.jar
```

This flag restores the JRE locale data as the primary source, falling back to CLDR. Use it while you audit locale-sensitive code for hard assertions on formatted output. The fix is to stop asserting on exact formatted strings — use structured date/time types (`LocalDate`, `ZonedDateTime`) and format only at the point of display, in tests that don't assert on the formatted string itself. Chapter 3.17 covers the failure mode and the fix.

## `--finalization=disabled`

Finalisation is on the removal path. `Object.finalize()` has been deprecated since JDK 9 and deprecated *for removal* since JDK 18 (JEP 421), and the JVM is increasingly aggressive about not running finalisers promptly or at all.

This flag disables all finaliser execution:

```bash
java --finalization=disabled -jar myapp.jar
```

It's a diagnostic tool, not a fix. Run your test suite with this flag. If something breaks — resource leaks, test failures, application misbehaviour — you have finaliser dependencies to address. If nothing breaks, you have confirmed that your application doesn't rely on finalisation for correctness. Chapter 3.22 covers the replacement patterns.

## `--add-opens` and `--add-exports`

These flags grant access to encapsulated JDK packages. They are workarounds, not fixes, and they belong in a tracking list with a deadline, not permanently in your startup configuration.

```bash
# Grant reflective access to java.lang package internals
--add-opens java.base/java.lang=ALL-UNNAMED

# Grant compile-time access to compiler internal APIs
--add-exports jdk.compiler/com.sun.tools.javac.api=ALL-UNNAMED
```

`--add-exports` grants access to the public types of a package its module does not export — needed both at compile time and at runtime for ordinary references to those types. `--add-opens` additionally opens the package for deep reflection (`setAccessible` on private members and constructors), and is a runtime concern.

Track every instance. A codebase with many of these flags has not migrated — it has deferred. The target state is zero `--add-opens` and zero `--add-exports` in your production configuration.

---

## The discipline rule

Every workaround flag in this chapter should have a corresponding issue in your tracking system. The issue records the flag, the reason it was added, the dependency or code path it covers, and a target date for resolution.

A project that adds `--add-opens` and records the issue will resolve it. A project that adds `--add-opens` without tracking it will still be running that flag five years from now.
