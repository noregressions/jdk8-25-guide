```
java.lang.InternalError: java.lang.reflect.InvocationTargetException
  ... at sun.font.FontManagerFactory ...
```

The last chapter of the catalogue is deliberately the odd one out: it is not a JDK 8→25 difference. Headless AWT text rendering — which every PDF library, chart generator, and image-stamping utility ultimately relies on — needs `fontconfig` and at least one font package from the operating system, and minimal container base images (Alpine and distroless variants especially) ship neither. The JVM's font subsystem then fails with an `InternalError` or NPE that says nothing about fonts.

---

## Why it's in a migration guide anyway

Because JDK upgrades and base-image changes travel together. The migration ticket says "move to JDK 25"; the implementation swaps `some-old-jdk8-image` for `eclipse-temurin:25-jre-alpine`; the old image happened to include fonts and the new minimal one doesn't — and the resulting production incident gets filed, wrongly, as a JDK 25 bug. Teams hit this *during* migrations, which makes it this guide's business even though the JDK is innocent.

It's also the category that most defeats local testing: developer machines and CI runners have fonts. The failure exists only inside the production image, which is why the Detect line insists on running the real rendering path in the real image.

**Verification status, stated plainly:** this is the one item of the 38 whose failure mode was not reproduced in this project's sandbox — the environment has 299 fonts installed and deliberately wasn't mutated to fake their absence (attempts via `FONTCONFIG_PATH` don't reliably reproduce it, and moving system font directories in a shared environment wasn't worth the risk). What *was* verified: the control case — identical, working rendering on both JDK 8 and 25 when fonts are present, confirming there's no cross-version difference to chase. The failure itself reproduces in one Docker command, included below for the day you have a daemon handy.

---

## Detect

In CI, inside the actual target image:

```bash
docker run --rm your-production-image java -cp /app FontSmokeTest
```

where the smoke test does the minimum: create a headless `BufferedImage`, get a `Graphics2D`, draw a string. Five lines that fail exactly where the report generator would, months earlier.

---

## Fix

Install fontconfig and one font package in the image:

```dockerfile
# Alpine
RUN apk add --no-cache fontconfig ttf-dejavu
# Debian/Ubuntu bases
RUN apt-get update && apt-get install -y --no-install-recommends fontconfig fonts-dejavu-core
```

That's the whole fix. The judgment call is which images need it: only those whose applications render text server-side — PDFs, charts, thumbnails, watermarks. Pure API services genuinely don't, and keeping their images minimal is the right call; the audit is "who calls into AWT", not "add fonts everywhere".

## Worked example

From [`examples/38-headless-font-rendering`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/38-headless-font-rendering) — control verified on Temurin 8u502 and 25.0.4; failure path documented for Docker:

```
fontconfig presence in this sandbox:  fc-list found: 299 font(s) registered

JDK 8,  headless rendering (control): rendered fine, font = java.awt.Font[family=SansSerif,...]
JDK 25, headless rendering (control): rendered fine, font = java.awt.Font[family=SansSerif,...]

Manual reproduction (needs Docker):
  docker run --rm -v "$JDK25_HOME:/jdk" -v "$PWD:/t" eclipse-temurin:25-jre-alpine \
    /jdk/bin/java -cp /t/out25 FontTest
  # expect: InternalError/NPE from the font subsystem
  # then: apk add fontconfig ttf-dejavu  → renders fine
```
