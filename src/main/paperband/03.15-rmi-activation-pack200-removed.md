```
Exception in thread "main" java.lang.NoClassDefFoundError: java/rmi/activation/ActivationSystem
```

Neither of these removals makes conference slides, because almost nobody *chose* them recently — and that is precisely the risk profile. Both APIs sit in code written fifteen to twenty-five years ago that has been quietly working ever since, in exactly the systems most likely to be doing an 8-to-25 migration today.

---

## What happened

**RMI Activation** (JDK 17, JEP 407) was the mechanism for lazily starting remote objects on demand via `rmid`. It was declared obsolete years before removal — optional since JDK 8, deprecated in 15 — and usage surveys found essentially none. The critical scoping point: **only the activation subsystem went.** Plain RMI — `java.rmi.Remote`, registries, exported objects — remains in JDK 25 and works. A hit on `java.rmi.activation` means surgery on the activation wiring, not a rewrite of your RMI layer.

**Pack200** (JDK 14, JEP 367) was a hyper-aggressive JAR compression format from the applet-download era, deeply coupled to the class-file format — which meant maintaining it taxed every bytecode change the platform made. Both the `java.util.jar.Pack200` API and the `pack200`/`unpack200` command-line tools were removed together (the tools' side of this appears in Chapter 3.34). Its habitat today is old distribution pipelines: installers, auto-updaters, and build scripts that pack JARs for download and unpack on install.

Neither has a replacement API, and neither needs one: activation's use cases died with the architectures that wanted them, and ordinary compression (or `jlink` runtime images, for the distribution case) does what Pack200 did without the coupling.

---

## Detect

```bash
grep -rE "java\.rmi\.activation|Pack200|pack200|unpack200" src/ scripts/ installer/
jdeps --class-path 'libs/*' app.jar | grep -E "rmi\.activation|jar\.Pack200"
```

Include build and installer scripts in the sweep — Pack200's most common survival site is a deployment pipeline rather than application code, where `jdeps` never looks.

---

## Fix

Remove the dependency; there is nothing to substitute in-place.

- **Activation:** re-export the remote objects as ordinary, always-running RMI services (which is how most "activatable" deployments effectively behaved anyway), or take the opportunity to move the interface to something current.
- **Pack200:** ship plain (or zlib-compressed) JARs — bandwidth arithmetic has moved on since 2004 — or, for genuinely size-sensitive distribution, build a `jlink` custom runtime image, which solves the size problem at a different and better layer.

## Worked example

From [`examples/15-rmi-activation-pack200-removed`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/15-rmi-activation-pack200-removed), verified on Temurin 8u502 and Temurin 25.0.4. Two one-liners, each referencing one removed API, compiled once on JDK 8 and run unmodified on both JDKs:

```
java.rmi.activation.ActivationSystem:
  JDK 8:
    java.rmi.activation.ActivationSystem
    exit=0
  JDK 25 (same .class, no recompile):
    Exception in thread "main" java.lang.NoClassDefFoundError: java/rmi/activation/ActivationSystem
    exit=1

java.util.jar.Pack200:
  JDK 8:
    com.sun.java.util.jar.pack.PackerImpl@6d06d69c
    exit=0
  JDK 25 (same .class, no recompile):
    Exception in thread "main" java.lang.NoClassDefFoundError: java/util/jar/Pack200
    exit=1
```

The same failure shape as the Java EE removals in Chapter 3.6 — class-load-time linkage errors in bytecode that compiled cleanly years ago — just from a quieter corner of the platform.
