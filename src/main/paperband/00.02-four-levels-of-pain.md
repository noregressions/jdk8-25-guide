Thirty-eight distinct ways a JDK 8 application can break on JDK 25 sounds unmanageable. It isn't — because every one of them belongs to one of four levels, and the level tells you three things at once: *when* the failure strikes, *how loudly* it announces itself, and *what order* to do the work in. This taxonomy is the spine of the book; every chapter in Part 3 carries its level in the opening table.

---

## Level 1 — Won't Start

The JVM refuses to launch. An obsolete GC flag, a Security Manager startup switch, a `java.ext.dirs` from a 2009 launch script — and the process exits before `main()`, before logging exists, before your APM agent attaches. The visible symptom in production is a restart loop with empty logs.

These failures are absolute, but they are also the *best* ones: deterministic, cheap to find (`java -version` with your production flags answers in seconds), and mechanical to fix. They come first because nothing else can even be tested until the JVM launches. Chapters 3.1–3.4.

## Level 2 — Crashes at Runtime

The application starts, then throws: `InaccessibleObjectException` from reflection on JDK internals, `NoClassDefFoundError` for removed Java EE packages, `ClassCastException` on the system classloader, `UnsupportedOperationException` from `setSecurityManager()` or `Thread.stop()`. Loud failures with stack traces — annoying, but honest. The trace names a class, the class names a chapter, the chapter names a fix.

The catch at this level is *coverage*: a crash only reveals itself on the code path that triggers it, so the rare branch — the December billing run, the error-handler that reflects — hides until it runs. This is why Part 1's runtime diagnostics matter as much as its static scanners. Chapters 3.5–3.15.

## Level 3 — Runs But Wrong

No crash. No exception. Tests pass, and the application is quietly incorrect: dates format differently (CLDR), files decode differently (UTF-8), security checks that used to block operations silently succeed, GC behaves to a different profile, lifecycle methods become no-ops. Nothing in any log announces that behaviour changed.

This is the level to fear, and the one the migration plan should over-invest in. Detection is never a stack trace — it is *comparison*: the same workload, the same inputs, run on both JDKs, outputs diffed. Chapters 3.16–3.24, and the baseline methodology in Chapter 1.6.

## Level 4 — Recompilation Surprises

The paradox level. Your JDK 8 *binaries* run happily on JDK 25 — and the moment you recompile the identical source, things change: `_` becomes a keyword, your `IO` class collides with `java.lang.IO`, computed `serialVersionUID`s shift and stored objects stop deserialising, Lombok's generated methods vanish, `-Werror` meets seventeen releases of new lint. (One entry — nestmates — changes in your favour.)

The practical rule this level enforces: **old binaries and recompiled binaries are two separate failure populations, and both need testing.** A migration that only proves "the old JAR still runs" has tested half the risk. Chapters 3.25–3.31.

---

## The fifth level: the environment

Four levels describe the application. A fifth describes everything around it — and in practice it often strikes *first*: the JDK's directory layout changed (`rt.jar` is gone), eight CLI tools left `bin/`, build toolchains have class-file-version floors, TLS defaults tightened, container memory ergonomics moved, minimal base images can't render fonts. None of this is your code, all of it can stop a migration, and most of it is invisible to every Java-side analysis tool. Chapters 3.32–3.38.

---

## Using the levels

The levels are a work-ordering algorithm as much as a taxonomy:

1. **Fix Level 1 first** — nothing else is testable until the JVM starts, and the fixes are mechanical.
2. **Flush out Level 2 with coverage** — run real workloads on the target JDK with `-Xlog:exceptions=info` (Chapter 1.7) watching for the exceptions frameworks swallow.
3. **Budget Level 3 the most time** — comparison testing is slower than crash-hunting, and it is the only method that works.
4. **Run Level 4 as its own pass** — recompile, then re-run everything, treating the results as a new application.
5. **Sweep the environment in parallel** — the flag audit, toolchain matrix, and container checks are independent of application testing and can start on day one.

That ordering is Chapter 0.3's five-day plan in embryo, and Part 5's playbook at full length. The taxonomy isn't academic — it is the reason the migration fits in a plan at all.
