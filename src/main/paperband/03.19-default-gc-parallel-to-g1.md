```
JDK 8:   -XX:+UseParallelGC
JDK 25:  -XX:+UseG1GC
```

Two flags the JVM chose for itself, eight releases apart. An application migrated with no explicit GC configuration changes collector — and therefore pause distribution, throughput profile, heap growth behaviour, and OOM characteristics — as a silent side effect of the version bump.

---

## What happened

JDK 8's default, Parallel GC, optimises for throughput and accepts long stop-the-world pauses. G1 — the default since JDK 9 (JEP 248) — trades a slice of throughput for predictable, bounded pauses and behaves differently across almost every operational dimension: shorter but more frequent pauses, different heap sizing instincts, different behaviour as occupancy climbs.

Neither collector is "wrong", which is exactly why this is a Runs But Wrong entry rather than a crash: the application works, and every number your team knows about it is obsolete. Latency SLOs measured under Parallel, alert thresholds tuned to its pause shape, capacity plans built on its footprint, load-test baselines — all describe a configuration that no longer exists. Teams either over-react ("the migration made everything slower!" — usually the throughput delta) or under-react (pause-shape alerts quietly stop firing because the pauses moved below thresholds designed for a different collector).

The GC evolution between 8 and 25 also runs deeper than the default swap: G1 itself gained a decade of improvement, and ZGC and Shenandoah (both with generational modes) now exist for genuinely pause-sensitive work. The default is a fine starting point; it is simply not *your JDK 8 baseline*.

---

## Detect

Selection is one command per JDK:

```bash
java -XX:+PrintCommandLineFlags -version 2>&1 | grep -o "\-XX:+Use[A-Za-z]*GC"
```

Behaviour is the real question, and the method is Chapter 1.6's: JFR recordings of the same workload on both JDKs, comparing pause distributions, allocation rates, and heap occupancy. Do it before cutover, so the first realistic G1 numbers your team sees are not production's.

---

## Fix

There is nothing to *repair* — the work is re-baselining:

1. Re-profile under realistic load on the target JDK and re-derive the numbers that matter (p99 pauses, throughput, footprint).
2. Update alert thresholds and capacity plans to the new baseline, not the remembered one.
3. Do **not** port old tuning forward — Parallel-era `NewRatio`/`SurvivorRatio` handiwork actively fights G1's heuristics, and Chapter 3.1 already covers how CMS flags fare. Start from defaults, tune only against measured need.
4. If measured need exists: stay on G1 and tune modestly, or evaluate ZGC for pause-dominated services. Explicit selection also inoculates you against the *next* default change.

## Worked example

From [`examples/19-default-gc-parallel-to-g1`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/19-default-gc-parallel-to-g1), verified on Temurin 8u502 and Temurin 25.0.4 — no GC configuration on either side:

```
JDK 8 default GC-related flags:
  -XX:+UseParallelGC

JDK 25 default GC-related flags:
  -XX:+UseG1GC
```

The test deliberately verifies only the deterministic part — that collector selection changes with zero configuration input. The throughput and pause deltas are real but workload-dependent, which is precisely why the fix is *your* JFR baseline rather than anyone's published benchmark.
