Upgrading a dependency during a JDK migration is a common and necessary step — many libraries require a newer version to support JDK 25. The version number of the new release tells you nothing useful about what changed at the API level. `japicmp` tells you the truth.

It compares two versions of a JAR and reports every API difference: added, removed, and modified classes, methods, and fields. More usefully, it distinguishes between *binary compatible* and *binary incompatible* changes — the difference between an upgrade that will work with your existing compiled code, and one that will fail at runtime with `NoSuchMethodError` or `IncompatibleClassChangeError`.

The version number lies. `japicmp` doesn't.

---

## What it finds

- Methods removed or added between versions
- Return type changes on existing methods
- Parameter type changes on existing methods
- Field type changes
- Access modifier changes (public → protected, etc.)
- Class hierarchy changes (superclass changed, interface added or removed)
- The binary/source compatibility classification for each change

For each change, `japicmp` classifies it as:

| Classification | Meaning |
|---|---|
| `BINARY COMPATIBLE` | Existing compiled code works against the new version without recompilation |
| `SOURCE COMPATIBLE` | Code recompiles cleanly against the new version. Whether existing class files still link is the separate, binary-compatibility question |
| `BINARY INCOMPATIBLE` | Existing class files that reference this API will throw at runtime |
| `SOURCE INCOMPATIBLE` | Code that uses this API will not compile against the new version |

---

## What it misses

`japicmp` analyses public API surface. It does not cover:

- Runtime behaviour changes that don't manifest as API changes (changed default values, altered algorithms)
- Internal implementation changes that affect performance
- Changes to serialisation form
- Security vulnerability status

It is a binary and source compatibility tool. It complements CVE scanning and EOL analysis; it doesn't replace them.

---

## Running japicmp

**Command line:**

```bash
java -jar japicmp.jar \
  --old libs/spring-core-5.3.30.jar \
  --new libs/spring-core-6.0.13.jar \
  --only-incompatible
```

**Maven plugin** — useful for CI integration:

```xml
<plugin>
  <groupId>com.github.siom79.japicmp</groupId>
  <artifactId>japicmp-maven-plugin</artifactId>
  <version>0.23.0</version>
  <configuration>
    <oldVersion>
      <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-core</artifactId>
        <version>5.3.30</version>
      </dependency>
    </oldVersion>
    <newVersion>
      <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-core</artifactId>
        <version>6.0.13</version>
      </dependency>
    </newVersion>
    <parameter>
      <onlyBinaryIncompatible>true</onlyBinaryIncompatible>
    </parameter>
  </configuration>
</plugin>
```

## Worked example

Comparing a library upgrade from version 1.0 to 2.0:

```
*** MODIFIED CLASS: com.example.DataService (not serializable)

=== MODIFIED METHOD: public String getDisplayName()
  RETURN TYPE: UNCHANGED
  BINARY COMPATIBLE

=== MODIFIED METHOD: public Object processData(String input)
  RETURN TYPE CHANGED: Object -> ProcessResult
  BINARY INCOMPATIBLE
  SOURCE COMPATIBLE

--- REMOVED METHOD: public void legacyProcess(String input, boolean flag)
  BINARY INCOMPATIBLE
  SOURCE INCOMPATIBLE

+++ NEW METHOD: public ProcessResult processData(String input, ProcessOptions options)
  BINARY COMPATIBLE (addition)
```

Working through this output:

**`processData` return type changed `Object` → `ProcessResult`**
This is binary incompatible. The method descriptor baked into a caller's bytecode includes the return type, so every compiled caller references `processData(String)` returning `Object` — a descriptor that no longer exists in the new version. Every one of them throws `NoSuchMethodError` at runtime, regardless of what the caller did with the result. Source compatible means the code will recompile against the new version — but the old compiled class files will fail.

**`legacyProcess` removed**
Both binary and source incompatible. Any compiled class that calls `legacyProcess` will throw `NoSuchMethodError`. Any source file that calls it will fail to compile. Find every call site and replace it before upgrading.

**`getDisplayName` return type unchanged, binary compatible**
No action needed. Your existing compiled code works against the new version.

**New overload of `processData`**
Adding a method is always binary compatible — no existing code references the new overload, so nothing can break. This is the new preferred API; migrate call sites to use `ProcessOptions` when convenient.

## When to run japicmp

Run it *before* committing to a dependency upgrade, not after. The workflow is:

1. Identify the dependency upgrade needed (minimum version for JDK 25 compatibility, or the latest available)
2. Run `japicmp` on old version vs new version
3. Review binary incompatible changes
4. Search your codebase for call sites that use the changed or removed APIs
5. Plan the source changes needed before or alongside the upgrade
6. Upgrade and validate

Skipping step 3 is how teams discover `NoSuchMethodError` in production on paths their tests didn't cover.

`japicmp` is also available as an online tool at `japicmp-frontend.fly.dev` — useful for a quick check without local setup.
