| **Level** | Runs But Wrong |
| **Introduced** | JDK 24 (JEP 486) |
| **Symptom** | `doPrivileged()` runs with no checks; `getSecurityManager()` always returns `null`; code expecting a `SecurityException` to block an operation never sees one |
| **Detect** | Manual audit: search for `catch (SecurityException`, `doPrivileged(`, `checkPermission(`, `getSecurityManager() != null` guards |

There is no error message to open this chapter with. That is the chapter.

The Security Manager's removal produces three failure shapes, and the other two announce themselves — a startup failure (Chapter 3.2) or a runtime exception (Chapter 3.8). This one is inverted: **code keeps running, and the thing that changes is that a security check stops happening.** An operation that policy used to block goes through. A permission gate evaluates to open. Nothing throws, nothing logs, no test fails unless a test asserts the *denial*.

---

## What happened

On JDK 24+ the Security Manager machinery is permanently disabled: `getSecurityManager()` always returns `null`, `doPrivileged()` executes its action with no checking, and `checkPermission()` never fires. Applications that used exception-driven control flow — attempt the operation, rely on `SecurityException` to stop the cases policy forbids — now take the success branch every time.

The worked example below shows the sharpest version, and it is worth understanding because the pattern is genuinely common. Code that installs a Security Manager defensively wraps the call in `try/catch` — a reasonable portability habit from an era when a framework might have installed one already. On JDK 25 that catch block quietly swallows the `UnsupportedOperationException` from Chapter 3.8, the process continues with no manager installed, and every downstream `if (sm != null)` guard becomes dead code. The application's own defensive robustness converts a loud failure into a silent permission escalation.

This is a security posture change, not merely a compatibility one. Whether it matters depends entirely on what the manager was enforcing: for many applications it was ceremonial; for plugin sandboxes, multi-tenant code execution, and document-rendering pipelines it was the enforcement layer.

---

## Detect

There is no tool for "a check that used to fire and now doesn't" — this is the one category in the catalogue that demands a manual audit. The search patterns that find the audit surface:

```bash
grep -rEn "catch \(SecurityException|doPrivileged\(|checkPermission\(|getSecurityManager\(\)" src/
```

For each hit, ask the only question that matters: *what did the application do when this check failed, and is it acceptable for that to now always succeed?* Pay particular attention to `catch (SecurityException` blocks containing real logic — fallbacks, denials, audit logging — because that logic is now unreachable. A test suite that asserts denials (attempt the forbidden operation, expect it blocked) is the one automated detector you can build, and worth building before the migration rather than after.

---

## Fix

Re-implement the enforcement at a layer that still exists: OS-level sandboxing and container policies (seccomp, read-only filesystems, network egress rules) for isolation; application-level authorisation for permission logic; separate processes for genuinely untrusted code. Then delete the dead Security Manager plumbing — leaving it in place invites the next reader to believe it still does something.

## Worked example

From [`examples/16-security-checks-silently-succeed`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/16-security-checks-silently-succeed), verified on Temurin 8u502 and Temurin 25.0.4. The test installs a deny-everything `SecurityManager` inside a defensive `try/catch`, then attempts a guarded operation:

```
JDK 8:
  getSecurityManager() = SecCheck$DenyingSecurityManager@70dea4e
  operation BLOCKED by SecurityException: java.lang.SecurityException: denied:
    ("java.security.AllPermission" "<all permissions>" "<all actions>")

JDK 25:
  could not install SecurityManager: java.lang.UnsupportedOperationException: Setting a Security Manager is not supported
  getSecurityManager() = null
  operation PROCEEDED (no security check enforced)
```

Read the JDK 25 run carefully: it did print a line — because this test deliberately logs its catch block. Production code that catches and continues without logging produces *nothing*. The operation that policy existed to prevent simply happens.
