```
Exception in thread "main" java.lang.UnsupportedOperationException: Setting a Security Manager is not supported
    at java.base/java.lang.System.setSecurityManager(System.java:304)
```

Most migration write-ups date this to JDK 24. That is when it became *unconditional* — but the exception first became the **default** behaviour in JDK 18, six releases earlier. Teams that migrated to JDK 18–23 and passed `-Djava.security.manager=allow` deferred the problem rather than escaping it: on JDK 24+ that same opt-out flag is itself a VM-initialisation failure (Chapter 3.2's category). Get the timeline right, because it determines whether "we already run on 21 fine" is evidence of safety or evidence of a deferred failure.

---

## What happened

The full sequence: deprecated for removal in JDK 17 (JEP 411). From JDK 18, JEP 411's plan took effect — `disallow` became the default value of the `java.security.manager` system property, so `setSecurityManager()` throws unless the deployment explicitly opted back in with `=allow`. JDK 24 (JEP 486) closed the window: the Security Manager cannot be enabled at all, from code or command line.

The callers are predictable: legacy app servers, OSGi-adjacent tooling like bndtools, custom sandboxing for plugin systems, and RMI setups that installed a manager as boilerplate. Unlike the startup-flag variant, this failure at least happens *after* `main()` — you get a stack trace in application logs naming the caller, which makes it the most diagnosable of the three Security Manager failure shapes.

---

## Detect

```bash
grep -rE "setSecurityManager|SecurityManager\(" src/
jdeprscan --for-removal --class-path 'libs/*' app.jar
```

`jdeprscan` reports it as `forRemoval=true since 17`, which names the *deprecation* release — remember the breakage arrives at 18 by default, not 17 (Chapter 1.2 covers this deprecated-vs-broken distinction).

---

## Fix

There is no replacement inside the JDK, and none is planned. Remove the installing code, then answer what the manager was actually doing at a different layer: OS or container sandboxing (seccomp, read-only filesystems, network policy) for the isolation cases; application-level authorisation for the permission cases. And audit what *stops happening* when the call is gone — code that relied on a `SecurityException` to block operations now proceeds silently, which is Chapter 3.16's category and the genuinely dangerous half of this removal.

## Worked example

From [`examples/08-setsecuritymanager-throws`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/08-setsecuritymanager-throws), verified on Temurin 8u502 and Temurin 25.0.4 — one call, three eras of behaviour:

```
JDK 8:
  set ok
  exit=0

JDK 25 (default):
  Exception in thread "main" java.lang.UnsupportedOperationException: Setting a Security Manager is not supported
      at java.base/java.lang.System.setSecurityManager(System.java:304)
      at SetSM.main(SetSM.java:3)
  exit=1

JDK 25 with -Djava.security.manager=allow (the JDK 18–23 opt-out flag):
  Error occurred during initialization of VM
  java.lang.Error: A command line option has attempted to allow or enable the Security Manager.
  Enabling a Security Manager is not supported.
  exit=1
```

The third run is the one worth staring at: the flag that *fixed* this exception on JDK 18–23 now prevents the VM from starting at all. A workaround carried forward across the JDK 24 boundary converts a diagnosable runtime exception into an empty-log startup failure.

One honesty note: the middle of that timeline — that `=allow` genuinely works on JDK 18–23 — is asserted from the JEP 411/486 documentation trail; the verification environment had only JDK 8 and 25 installed. If you run a JDK 18–23 build, the one-minute check is in the test's README.
