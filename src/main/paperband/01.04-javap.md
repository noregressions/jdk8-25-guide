`javap` is the JDK's class file disassembler. It turns compiled bytecode back into something human-readable — not source code, but a precise description of what the bytecode declares and does. For migration work, it's the tool you reach for when the other tools have told you *something is wrong* and you need to know *exactly what*.

It's also the tool that makes the recompilation paradox visible. Compile the same source file against JDK 8 and against JDK 25, run `javap` on both outputs, and the differences tell you precisely what changed in the bytecode — and what that means at runtime.

---

## What it finds

- **Class file version** — the JDK version a class file was compiled against
- **Method and field descriptors** — the exact type signatures the JVM uses to resolve calls at runtime
- **NestHost and NestMembers attributes** — the nestmate access model introduced in JDK 11
- **Module attributes** — module declarations, exports, and requirements
- **String concatenation strategy** — `StringBuilder` chains (JDK 8) vs `invokedynamic` (JDK 9+)
- **Constant pool references** — every class, method, and field the bytecode references symbolically
- **Bytecode instructions** — the full instruction sequence for any method

---

## What it misses

`javap` operates on a single class file at a time. It does not analyse cross-class dependencies (use `jdeps` for that), it does not evaluate runtime behaviour, and it does not report on the JDK APIs being called — only on what the bytecode symbolically references.

---

## Key flags

| Flag | Purpose |
|------|---------|
| `-c` | Disassembles the bytecode instructions for each method. |
| `-v` | Verbose output: includes the constant pool, class file version, flags, attributes, and stack frame data. The flag you will use most for migration diagnostics. |
| `-p` | Includes private members in the output. Without this, private fields and methods are hidden. |
| `-s` | Prints internal type signatures (useful for matching against `NoSuchMethodError` messages). |
| `--module <name>` | Disassembles a class from a named module rather than the file system. |

## Reading the class file version

Every class file carries a major version number in its header. This tells you which JDK compiled it — and whether the JVM you're running on can load it.

| Major version | JDK |
|--------------|-----|
| 52 | JDK 8 |
| 55 | JDK 11 |
| 61 | JDK 17 |
| 65 | JDK 21 |
| 69 | JDK 25 |

```bash
javap -v MyClass.class | grep "major version"
```

```
major version: 52
```

A class file with major version 52 was compiled against JDK 8. It will load on any JDK 8 or later JVM — the JVM is backward-compatible with old class files. The reverse is not true: new class files do not run on old JVMs, so a class file with major version 69 will only load on JDK 25 or later. If an ASM-based tool in your stack tries to parse a version 69 class file and doesn't support it, you get `IllegalArgumentException: Unsupported class file major version 69`. Chapter 3.12 covers this failure mode.

## Worked example: diagnosing a NoSuchMethodError

`NoSuchMethodError` at runtime means the JVM found the class but couldn't resolve the method reference baked into the calling code's bytecode. `javap` shows you exactly what the caller expected to find.

```bash
javap -c -v -p com/example/data/UserService.class | grep -A2 'Methodref'
```

```
#42 = Methodref  com/example/data/UserRepository.findById:(Ljava/lang/Long;)Ljava/util/Optional;
#43 = Methodref  com/example/data/UserRepository.save:(Ljava/lang/Object;)Ljava/lang/Object;
```
{.fs--1}

This tells you that `UserService` was compiled against a version of `UserRepository` where `findById` returns `Optional<User>` and `save` takes an `Object`. If the `UserRepository` JAR has since been updated and `save` now takes `User` directly, the method descriptor no longer matches — and the JVM throws `NoSuchMethodError` even though a method named `save` exists.

This is the exact difference between binary-compatible and binary-incompatible API changes. `javap` makes it explicit. `japicmp` (Chapter 1.8) automates this comparison across entire JARs.

## Worked example: the recompilation paradox in action

Compile the same string concatenation code against JDK 8 and JDK 25:

```java
public String describe(String name, int value) {
    return "Name: " + name + ", Value: " + value;
}
```

**Compiled on JDK 8** (`javap -c`):

```
public java.lang.String describe(java.lang.String, int);
  Code:
     0: new           #2  // class java/lang/StringBuilder
     3: dup
     4: invokespecial #3  // Method StringBuilder."<init>":()V
     7: ldc           #4  // String "Name: "
     9: invokevirtual #5  // Method StringBuilder.append:(Ljava/lang/String;)
    12: aload_1
    13: invokevirtual #5  // Method StringBuilder.append:(Ljava/lang/String;)
    16: ldc           #6  // String ", Value: "
    18: invokevirtual #5  // Method StringBuilder.append:(Ljava/lang/String;)
    21: iload_2
    22: invokevirtual #7  // Method StringBuilder.append:(I)
    25: invokevirtual #8  // Method StringBuilder.toString:()
    28: areturn
```
{.fs--1}

**Compiled on JDK 25** (`javap -c`):

```
public java.lang.String describe(java.lang.String, int);
  Code:
     0: aload_1
     1: iload_2
     2: invokedynamic #7, 0  // InvokeDynamic makeConcatWithConstants:(Ljava/lang/String;I)Ljava/lang/String;
     7: areturn
```
{.fs--1}

Same source. Completely different bytecode. The JDK 25 version is shorter, faster, and produces less garbage. What changes is the bytecode *shape*: the chain of `StringBuilder.append` calls collapses into a single `invokedynamic` call site bound to `makeConcatWithConstants`. Observable behaviour — including the order in which side effects run — is identical: the JLS mandates left-to-right operand evaluation regardless of compilation strategy. The shape change is what matters, and it matters to bytecode tooling: agents, ASM-based instrumentation, and anything that pattern-matches on `StringBuilder` chains will no longer find them in recompiled code. `javap` is how you see the difference.

## Worked example: nestmate attributes

Inner class private access changed fundamentally in JDK 11. Before JDK 11, the compiler generated synthetic bridge methods to allow an outer class to access private members of an inner class. After JDK 11, it uses the `NestHost` and `NestMembers` attributes instead.

**JDK 8 compiled inner class** (`javap -v -p`):

```
static int access$000(com.example.Outer);   // synthetic bridge method
  descriptor: (Lcom/example/Outer;)I
  flags: (0x1008) ACC_STATIC, ACC_SYNTHETIC
```

**JDK 11+ compiled inner class** (`javap -v`):

```
NestHost: class com/example/Outer
```

The bridge method is gone. The nestmate relationship is declared at the class file level instead. The behaviour is identical; the bytecode is cleaner. This is the one recompilation surprise that works in your favour — Chapter 3.31 covers it.
