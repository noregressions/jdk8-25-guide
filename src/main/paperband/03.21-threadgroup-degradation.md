`ThreadGroup` is the strangest entry in this catalogue because it degrades in both directions at once. Some of its methods fail silently:

```
JDK 25: destroy() returned normally, isDestroyed() after = false
```

and one fails harder than almost anything else in Part 3:

```
JDK 25: tg.stop() threw: java.lang.NoSuchMethodError: 'void java.lang.ThreadGroup.stop()'
```

The object still exists. It just doesn't do what you told it to — until it can't even be asked.

---

## What happened

`ThreadGroup` was Java 1.0's thread-management story, and Project Loom's rework of the threading model (JDK 19–21) finished a dismantling that had started earlier. The pieces went separately: from JDK 16, `destroy()` became a silent no-op and daemon status is ignored. The lifecycle trio was degraded to throw `UnsupportedOperationException` (JDK 19–20) and then **removed from the class entirely in JDK 23** — `stop()` via JDK-8320786, `suspend()`/`resume()` via JDK-8320532, alongside `Thread`'s own suspend/resume.

That removal is the detail most write-ups get wrong — including earlier material in this project, which described `ThreadGroup.stop()` as "throwing since JDK 20" by analogy with `Thread.stop()` (Chapter 3.10). The analogy fails in the direction that matters: `Thread.stop()` on JDK 25 still throws a catchable `UnsupportedOperationException`; `ThreadGroup.stop()` produces `NoSuchMethodError` — a linkage error — for old compiled callers, and doesn't compile at all for new ones. A defensive `catch (UnsupportedOperationException)` written for the `Thread` case does nothing here.

The silent half is the classic Runs But Wrong shape: code that calls `tg.destroy()` in a cleanup path, or configures daemon thread groups for automatic teardown, keeps executing without error while the behaviour it was written for simply doesn't occur. Whether that matters ranges from "not at all" (most modern code never touches `ThreadGroup`) to resource leaks in long-lived applications built on 1990s thread-management patterns — app-server-era connection managers and hand-rolled worker pools being the usual suspects.

## Detect

```bash
grep -rEn "ThreadGroup" src/ | grep -vE "getThreadGroup\(\)\s*==|Thread\.currentThread"
```

Then classify each hit: reads (`activeCount()`, enumeration — still functional, if long deprecated in spirit) versus lifecycle writes (`destroy()`, `stop()`, `suspend()`, `resume()`, `setDaemon(true)` — all inert or gone). For the removed methods, a recompile against JDK 25 is the definitive detector: they fail to compile.

---

## Fix

Move lifecycle management to `ExecutorService` and explicit tracking — there is no drop-in replacement for `ThreadGroup`'s old semantics, because those semantics (asynchronously killing or suspending groups of threads) were retired for the same correctness reasons as `Thread.stop()`. Group teardown becomes `shutdown()`/`shutdownNow()` on the executor that owns the threads; "daemon group" becomes creating daemon threads via a `ThreadFactory`. Purely observational uses of `ThreadGroup` can usually just be deleted — modern diagnostics (JFR, `jcmd Thread.print`) answer the same questions better.

## Worked example

From [`examples/21-threadgroup-degradation`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/21-threadgroup-degradation), verified on Temurin 8u502 and Temurin 25.0.4 — two independent checks, because the two methods degrade differently. `stop()` was compiled once under JDK 8 (it no longer compiles on 25 at all) and run unmodified on both:

```
-- ThreadGroup.stop(), JDK-8-compiled class, run on JDK 8: --
  tg.stop() returned normally

-- ThreadGroup.stop(), SAME JDK-8-compiled class, run on JDK 25 (no recompile): --
  tg.stop() threw: java.lang.NoSuchMethodError: 'void java.lang.ThreadGroup.stop()'

-- ThreadGroup.destroy(), JDK 8: --
  isDestroyed() before = false
  destroy() returned normally, isDestroyed() after = true

-- ThreadGroup.destroy(), JDK 25: --
  isDestroyed() before = false
  destroy() returned normally, isDestroyed() after = false
```

The `destroy()` runs are the ones to sit with: identical code, identical "success", opposite outcomes — and only the return value of a method nobody checks (`isDestroyed()`) tells you which world you're in.
