`jdeps` tells you which internal APIs your code is using. `jdeprscan` asks a different question: which APIs you're using are *scheduled to disappear*?

The JDK deprecation mechanism has two tiers. Ordinary `@Deprecated` marks an API as discouraged — it will probably stay in the platform indefinitely, it just signals that there's a better way. `@Deprecated(forRemoval=true)` is a commitment: the API will be removed in a future release. `jdeprscan --for-removal` finds every usage of that second tier in your compiled code. These are not style warnings. They are ticking clocks.

---

## What it finds

`jdeprscan` scans compiled class files and JARs for calls to JDK APIs marked `@Deprecated(forRemoval=true)`. The key findings for a JDK 8 to 25 migration are:

- `System.setSecurityManager()` and related Security Manager methods — throw `UnsupportedOperationException` by default since JDK 18, unconditionally since JDK 24
- `Object.finalize()` overrides — finalisation is on the removal path
- `Thread.stop()` — throws `UnsupportedOperationException` since JDK 20; `Thread.suspend()` and `Thread.resume()` — degraded to throw in JDK 19/20, removed in JDK 23
- `Runtime.exec()` overloads deprecated in JDK 18
- Various `java.lang` and `java.util` methods deprecated across JDK 9 to 25
- References to the Java EE modules removed in JDK 11 (detected at compile time against JDK 11+)

---

## What it misses

`jdeprscan` only knows about JDK APIs. It will not flag:

- Deprecated APIs in third-party libraries
- APIs that are deprecated but not marked `forRemoval=true`
- Runtime behaviour changes that don't involve a deprecated API call
- EOL status of your dependencies — that is a supply chain question, covered in Chapter 1.10

It also operates on compiled bytecode. If your code calls a deprecated method via reflection at runtime, `jdeprscan` will not find it.

---

## Key flags

| Flag | Purpose |
|------|---------|
| `--for-removal` | Filters to only APIs deprecated for removal. Use this flag every time — without it, the output includes everything marked `@Deprecated`, which is far too noisy to be useful. |
| `--release <n>` | Checks against the deprecated API list for a specific JDK release. Useful for targeting a specific migration step rather than the current JDK. |
| `--class-path` | Specifies additional JARs needed to resolve the scanned class files. |
| `-v` / `--verbose` | Enables additional message output during processing. To include APIs deprecated ordinarily (without `forRemoval=true`), simply omit `--for-removal`. |

## Worked example

```bash
jdeprscan \
  --for-removal \
  --class-path 'libs/*' \
  myapp.jar
```

Example output:

```
class com/example/security/AppSecurityManager uses deprecated method
  java/lang/System::setSecurityManager(Ljava/lang/SecurityManager;)V
  (forRemoval=true since 17)

class com/example/data/CacheEntry uses deprecated method
  java/lang/Object::finalize()V
  (forRemoval=true since 18)

class com/example/util/ThreadController uses deprecated method
  java/lang/Thread::stop()V
  (forRemoval=true since 18, behaviour changed since 20)

```

A second run *without* `--for-removal` widens the net to ordinary deprecations,
which is where findings like this appear:

```
class com/example/io/LegacyReader uses deprecated method
  java/lang/Runtime::exec(Ljava/lang/String;)Ljava/lang/Process;
  (deprecated since 18)
```

Working through this output:

**`System::setSecurityManager` — forRemoval since 17**
This code is installing a custom Security Manager at runtime. On JDK 24 and later, this call throws `UnsupportedOperationException` unconditionally. There is no workaround flag. The Security Manager is gone. Chapter 3.8 covers the replacement approaches.

**`Object::finalize` — forRemoval since 18**
`CacheEntry` overrides `finalize()` to clean up resources. This is a resource management issue: the JVM is increasingly unwilling to run finalisers promptly or at all. The fix is `try-with-resources` for deterministic cleanup, or the `Cleaner` API for background cleanup of resources that cannot use try-with-resources. Chapter 3.22 covers both paths.

**`Thread::stop` — forRemoval since 18**
`Thread.stop()` has been deeply problematic since Java 1.2 — it releases all monitors held by the thread as it terminates, leaving objects in inconsistent states. The JDK eventually stopped pretending this was safe. On JDK 20 and later, calling it throws `UnsupportedOperationException`. Use thread interruption and cooperative cancellation instead. Chapter 3.10 covers the pattern.

**`Runtime::exec(String)` — deprecated since 18 (not for removal; reported only without `--for-removal`)**
The single-string overload of `Runtime.exec()` is deprecated because it relies on platform-specific tokenisation of the command string, which behaves differently across operating systems. Use `ProcessBuilder` instead, which accepts an explicit argument list and is unambiguous across platforms.

## Interpreting the output

The `since` version in the output is important context. An API deprecated for removal since JDK 9 has been on the removal path for sixteen releases — it could go in any future JDK. One deprecated since JDK 23 is more recent but the trajectory is the same.

A useful way to triage the findings:

**Already removed or degraded** — check the `since` version against the removal history. `System.setSecurityManager()` has not been removed, but it throws `UnsupportedOperationException` — by default since JDK 18 (JEP 411 made `disallow` the default value of `java.security.manager`, with `-Djava.security.manager=allow` as the opt-out through JDK 23), and unconditionally since JDK 24 (JEP 486). If you're targeting JDK 25, this is a blocker. Cross-reference Part 2 for the removal version of each finding.

**Behaviour already changed** — `Thread.stop()` throws since JDK 20 even though it's still in the API (`Thread.suspend()` and `Thread.resume()` went further: degraded to throw in JDK 19/20, removed in JDK 23). The class exists; calling it fails. The `jdeprscan` output names the *deprecation* version, not the *breakage* version. Always check Part 3 for the actual failure mode.

**Removal pending** — APIs still present in JDK 25 but on the removal path. Not blockers today, but plan the fix. Any codebase you migrate to JDK 25 should leave no `forRemoval` findings unresolved, because the next migration will be to JDK 27 or 29, and some of them will be gone by then.

Run `jdeprscan` on your dependencies as well as your own code. A library that calls `System.setSecurityManager()` will fail at runtime on JDK 24+ whether it's your code or not.
