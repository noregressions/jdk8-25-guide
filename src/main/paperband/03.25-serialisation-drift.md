```
java.io.InvalidClassException: Payload$Nested; local class incompatible:
stream classdesc serialVersionUID = 9055674887718378473,
local class serialVersionUID = -1260671151154697526
```

No source changed. The same file, compiled by two `javac` versions, produced two classes that refuse to exchange data — because the class never declared its own `serialVersionUID` and quietly trusted the compiler to compute a stable one. Across a JDK 8 → 25 recompile, it doesn't.

---

## What happened

When a `Serializable` class omits `serialVersionUID`, the runtime computes one by hashing the class's structure — including **synthetic members the compiler generated**. That last part is the trap: synthetic members are an implementation detail that changed between JDK 8 and modern `javac`. The clearest mechanism is the nestmate change (Chapter 3.31): pre-JDK 11, an inner class whose private members were touched by its enclosing class carried a synthetic `access$000` bridge method; nestmates eliminated it. Same source, one fewer method in the hash, different UID.

The operational shape is nastier than a code bug: an application serialises objects into a database column, cache, message queue, or HTTP session store for years under JDK 8. A routine recompile on JDK 25 — no functional change, no review flag — and every previously stored object throws `InvalidClassException` on read. The failure arrives at *deserialisation time*, in production, pointed at data rather than code.

Note what does **not** trigger this: old binaries running unchanged on JDK 25 keep their old UID — this is a pure recompilation surprise. And note what does not reliably prevent it: anything short of an explicit UID leaves you exposed to the next compiler-internal change, whatever it is.

---

## Detect

```bash
grep -rlE "implements .*Serializable" src/ | xargs grep -L "serialVersionUID"
```

Every file that list produces is carrying a computed UID. For classes with instances already in storage, capture the *historical* UID before anything is recompiled — run `serialver` against the **old** build's classpath:

```bash
serialver -classpath old-build/classes com.example.SessionPayload
```

That number is the one your stored data expects, and the one to pin.

---

## Fix

Declare `serialVersionUID` explicitly on every `Serializable` class — using the `serialver`-captured value where stored data exists, so old streams keep deserialising. This is a mechanical, scriptable change and the single highest-value hour in this whole level of the catalogue.

The structural fix, for the longer arc: Java's built-in serialisation is a liability the platform itself is edging away from — move persistent and cross-process data to explicit formats (JSON, Protobuf, Avro) where schema evolution is a designed-for feature rather than a hash collision. Reserve that for the roadmap; the explicit UID is the migration-week action.

## Worked example

From [`examples/25-serialisation-drift`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/25-serialisation-drift), verified on Temurin 8u502 and Temurin 25.0.4. `Payload.Nested` is `Serializable`, has no explicit UID, and its private field is read by the enclosing class — the exact pattern that grows a synthetic bridge under `javac8` and loses it under `javac25`:

```
Synthetic methods on Payload$Nested, javac8-compiled:   count: 1
Synthetic methods on Payload$Nested, javac25-compiled:  count: 0

Write with JDK 8 (Payload$Nested compiled by javac8):
  wrote obj.ser

Read with JDK 25 (Payload$Nested RECOMPILED by javac25 — identical source):
  java.io.InvalidClassException: Payload$Nested; local class incompatible:
  stream classdesc serialVersionUID = 9055674887718378473,
  local class serialVersionUID = -1260671151154697526
```

One synthetic method's existence is the entire difference between those two nineteen-digit numbers.
