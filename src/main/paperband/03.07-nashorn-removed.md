This category's defining feature is that the exception points at the wrong place:

```
engine = null
Exception in thread "main" java.lang.NullPointerException: Cannot invoke
"javax.script.ScriptEngine.eval(String)" because "<local2>" is null
```

Nashorn — the JavaScript engine bundled since JDK 8 — was deprecated in JDK 11 (JEP 335) and removed in JDK 15 (JEP 372). But `javax.script` (JSR 223), the API used to *reach* it, is still in the JDK and works fine. So the lookup doesn't throw; it politely returns `null`, per the `ScriptEngineManager` contract for an unknown engine. The `NullPointerException` arrives wherever the code first uses the result — which in real applications can be a different class, a different module, or a lazily-initialised path that only runs for certain inputs.

That gap between cause and symptom is why this failure gets misdiagnosed as "something wrong with the script" or chased as an intermittent NPE, when the engine was simply never there.

---

## What happened

Applications used embedded JavaScript for rule engines, configuration DSLs, templating, and user-supplied formulas — often deep inside a library rather than in first-party code. On JDK 8 the `"nashorn"`, `"js"`, and `"javascript"` names all resolved to the bundled engine. From JDK 15 they resolve to nothing, and any `ScriptEngine` obtained by name should be treated as nullable.

---

## Detect

```bash
grep -rE "getEngineByName|ScriptEngineManager|nashorn" src/ libs-sources/
```

Search dependencies too — rule-engine and templating libraries are the classic indirect carriers. A runtime canary is trivial and worth putting in a startup health check if scripting matters to the application:

```java
Objects.requireNonNull(
    new ScriptEngineManager().getEngineByName("nashorn"),
    "JavaScript engine not available on this JDK");
```

---

## Fix

Two replacement routes, both external dependencies:

1. **Standalone Nashorn** (`org.openjdk.nashorn:nashorn-core`) — the same engine, maintained as a separate project. Lowest-friction option for existing Nashorn script bodies; it registers under the same engine names.
2. **GraalJS** (`org.graalvm.js` artefacts) — a current JavaScript implementation with a Nashorn compatibility mode for the old engine's non-standard behaviours. The right choice when the scripts are actively developed rather than frozen.

Either way, add defensive null-handling at every `getEngineByName` call site so the *next* engine change fails with a message naming the actual problem.

---

## Worked example

From [`examples/07-nashorn-removed`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/07-nashorn-removed), verified on Temurin 8u502 and Temurin 25.0.4:

```java
ScriptEngine e = m.getEngineByName("nashorn");
System.out.println("engine = " + e);
Object result = e.eval("1+1");   // NPE here — not at the lookup
```

```
JDK 8:
  engine = jdk.nashorn.api.scripting.NashornScriptEngine@64bfbc86
  result = 2
  exit=0

JDK 25:
  engine = null
  Exception in thread "main" java.lang.NullPointerException: Cannot invoke
  "javax.script.ScriptEngine.eval(String)" because "<local2>" is null
      at Nashorn.main(Nashorn.java:7)
  exit=1
```

One small mercy of the modern JDK: helpful NullPointerExceptions (JDK 14+) at least name the null expression. On a JDK-8-era mental model — "we ship a JavaScript engine" — the message still says nothing about *why* it is null.
