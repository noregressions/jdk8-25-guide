Before you change a line of code or update a single dependency, audit your JVM startup flags. This takes an hour and can prevent the most frustrating class of migration failure: the application that refuses to start before you even get to test anything.

JDK 25 rejects flags it doesn't recognise. If your startup scripts, Docker entrypoints, or Kubernetes deployment manifests contain a flag that was removed between JDK 8 and JDK 25 — and several were — the JVM prints an error and exits immediately. Your application never starts. Your tests tell you nothing. The error message names the flag but gives no migration context.

---

## What the audit finds

The `PrintFlagsFinal` technique compares the complete set of JVM flags between your current JDK and your target JDK. It surfaces:

- **Removed flags** — flags the target JDK no longer accepts, causing startup failure
- **Changed defaults** — flags that exist in both JDKs but whose default values changed, silently altering behaviour
- **New flags** — flags available in the target JDK that might be relevant to your configuration
- **Renamed flags** — flags that exist under a different name in the target JDK

The most significant removals for a JDK 8 to 25 migration:

| Removed flag | Removed in | Replacement |
|---|---|---|
| `-XX:+UseConcMarkSweepGC` | Deprecated JDK 9, obsolete JDK 14 (JEP 363), expired JDK 15 | `-XX:+UseG1GC` or `-XX:+UseZGC` |
| `-XX:+CMSIncrementalMode` | JDK 14 | No equivalent — incremental CMS had no replacement |
| `-XX:+UseParNewGC` | JDK 14 | G1 handles young generation collection internally |
| `-XX:MaxPermSize` | Ignored with a warning on JDK 8 (PermGen already removed); rejected outright on modern JDKs | `-XX:MaxMetaspaceSize` |
| `-XX:PermSize` | Same as above | `-XX:MetaspaceSize` |
| `-XX:+PrintGCDetails` | Not removed — kept as a deprecated alias; still works on JDK 25 with a deprecation warning | `-Xlog:gc*` |
| `-XX:+PrintGCTimeStamps` | JDK 9 (startup-fatal on modern JDKs) | `-Xlog:gc*::time` |
| `-verbose:gc` | Not removed — kept as an alias | `-Xlog:gc` |
| `-Djava.security.manager` | JDK 24 (fatal error) | No replacement — Security Manager is gone |

Changed defaults worth knowing about:

| Flag | JDK 8 default | JDK 25 default | Effect |
|---|---|---|---|
| `UseG1GC` | `false` (Parallel GC was default) | `true` | GC behaviour and pause profile changes |
| `UseCompactObjectHeaders` | N/A | `false` (product option in JDK 25, JEP 519) | Object layout changes — affects cached Unsafe offsets |

One flag worth a note despite *not* changing: `MaxRAMPercentage` (available from JDK 8u191) defaults to 25.0 and is unchanged through JDK 25. If a container suddenly gets a much larger heap after migration, the JVM default is not the culprit — beware vendor container images and buildpacks that set `-XX:MaxRAMPercentage` themselves; that is where surprise heap-size changes come from.

## The technique

Capture the full flag set for both JDKs and diff them:

```bash
# Capture JDK 8 flags
java8 -XX:+PrintFlagsFinal -version 2>&1 | sort > flags-jdk8.txt

# Capture JDK 25 flags
java25 -XX:+PrintFlagsFinal -version 2>&1 | sort > flags-jdk25.txt

# Diff them
diff flags-jdk8.txt flags-jdk25.txt | grep "^[<>]"
```
{.fs--1}

Lines prefixed `<` exist in JDK 8 but not JDK 25 — these are removed or renamed. Lines prefixed `>` exist in JDK 25 but not JDK 8 — these are new or renamed.

For a visual comparison across any JDK version combination, the VM Options Explorer at `chriswhocodes.com/vm-options-explorer.html` is an excellent alternative to the manual diff. It covers every JDK from 6 to 25 and lets you filter by flag name or compare two versions side by side.

## Worked example

Running the diff on a typical JDK 8 configuration that includes CMS flags:

```
< bool UseConcMarkSweepGC = false {product} {default}
< uintx MaxPermSize = 85983232 {product} {default}
< bool PrintGCDetails = false {product} {default}
< bool PrintGCTimeStamps = false {product} {default}
< uintx CMSInitiatingOccupancyFraction = 92 {product} {default}
> bool UseCompactObjectHeaders = false {product} {default}
> size_t MaxMetaspaceSize = 18446744073709547520 {product} {default}
> bool UseZGC = false {product} {default}
```

**`UseConcMarkSweepGC`** — CMS was deprecated in JDK 9, made obsolete in JDK 14 (JEP 363), and the flag expired in JDK 15. If this flag appears in your startup configuration with value `true`, the JVM will refuse to start on JDK 25. Even with value `false`, the flag is unrecognised and will cause a startup failure on JDK 25 (unrecognised flags are fatal regardless of value).

**`MaxPermSize`** — PermGen was removed in JDK 8. The flag is ignored with a warning on JDK 8 and rejected outright on modern JDKs. Replace with `-XX:MaxMetaspaceSize` if you need to bound metaspace growth.

**`PrintGCDetails` / `PrintGCTimeStamps`** — the old GC logging flags were replaced by the unified logging framework in JDK 9, but they did not all go the same way. `-XX:+PrintGCDetails` (like `-verbose:gc`) survives as a kept, deprecated alias — it prints a deprecation warning and translates to `-Xlog:gc*` — while `-XX:+PrintGCTimeStamps` and most of the rest of the `PrintGC*` family are startup-fatal on modern JDKs. Chapter 3.3 covers the conversion to `-Xlog:gc*` syntax.

**`UseCompactObjectHeaders`** — a new product option in JDK 25 (JEP 519), off by default. If your application caches `Unsafe.objectFieldOffset()` results, the compact headers feature can invalidate those cached values. Chapter 3.20 covers this in detail.

## Where to look for flags

JVM flags accumulate in surprising places. A thorough audit covers:

- Application server startup scripts (`standalone.sh`, `catalina.sh`, etc.)
- Docker entrypoints and `CMD` / `ENTRYPOINT` lines in Dockerfiles
- Kubernetes deployment manifests — `JAVA_OPTS` environment variables
- CI/CD pipeline configurations — Maven Surefire plugin `argLine` properties
- IDE run configurations — sometimes the only place a flag exists
- Environment variables: `JAVA_OPTS`, `JVM_OPTS`, `MAVEN_OPTS`, `GRADLE_OPTS`
- `jvm.options` files in application server configurations

The flags in CI/CD and IDE configurations are the ones most likely to be forgotten. A flag that has lived in a developer's IntelliJ run configuration for six years won't surface until that developer tries to run the migrated application locally.
