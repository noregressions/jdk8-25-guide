If you're still running Java 8 in production, you are not alone. Just under 30% of production Java applications were still running JDK 8 in New Relic's 2024 State of the Java Ecosystem report — and the number falls only slowly. That's a platform that stopped receiving free public security updates in 2019. The engineers who built those applications weren't reckless. Java 8 was stable, well-understood, and extraordinarily well-supported. Staying on it made sense, right up until it didn't.

The gap between JDK 8 and JDK 25 is the largest change to the Java platform in its three-decade history. Seventeen releases. The module system rewrote the rules of visibility. Internal APIs were progressively walled off, then locked down, then made into hard errors. Entire packages — Java EE, CORBA, the Nashorn JavaScript engine — were removed from the JDK entirely. The default charset changed. The Security Manager, a pillar of the Java security model since JDK 1.0, was permanently disabled (JDK 24, JEP 486). Every release since JDK 9 has added new ways for old code to behave differently.

This guide exists because migration at this scale is manageable — but only if you know what you're looking for.

---

## Who this guide is for

This guide is written for practitioners: the developers, architects, and platform engineers who own the migration work, or who are trying to understand the scope of it before committing to a plan.

It assumes working knowledge of Java development. It does not assume familiarity with the changes introduced after JDK 8 — that's the point. It is organised so that a developer who hits a specific runtime failure can navigate directly to the relevant chapter without reading everything that precedes it. It is equally useful as a planning tool for teams assessing the migration surface before writing a single line of code.

## How to use this guide

Two short chapters follow this introduction and frame everything else: **the four levels of pain** (Chapter 0.2) — the failure taxonomy the whole guide is organised around — and **what to do on Monday morning** (Chapter 0.3), a five-day reconnaissance plan you can run without budget approval or a formal project. If you read nothing else this week, read those two.

The guide then has five parts, designed to be used independently as well as together.

**Part 1 — The diagnostic toolkit** covers the tools you run before you change anything. `jdeps`, `jdeprscan`, `jnativescan`, JDK Flight Recorder, and the others. Each chapter explains what the tool finds, what it misses, and how to interpret the output. If you want to understand your exposure before starting, start here.

**Part 2 — Challenges by JDK level** is organised by migration step: 8 to 11 (Chapter 2.1), 11 to 17 (2.2), 17 to 21 (2.3), and 21 to 25 (2.4). Each chapter maps what lands in that range, at a paragraph per change, and points into Part 3 for the depth. If your question is "what's between me and JDK 25?", find your starting version and read from there.

**Part 3 — The failure catalogue** is the core of the book: thirty-eight chapters, one per failure category, grouped by level — Won't Start (3.1–3.4), Crashes at Runtime (3.5–3.15), Runs But Wrong (3.16–3.24), Recompilation Surprises (3.25–3.31), and the environment, distribution and build toolchain (3.32–3.38). Each chapter opens with the exact error message or symptom, and closes with a worked example verified on real JDK 8 and JDK 25 builds. If you've hit a specific error — `InaccessibleObjectException`, `NoClassDefFoundError` for a `javax` class, `InvalidClassException` on deserialisation — go directly to the relevant chapter.

**Part 4 — Dependency health and supply chain** covers the migration risk that the JDK's own tools cannot see: unmaintained libraries, EOL components, the tool landscape, and the supply chain exposure that follows you regardless of which JDK you're targeting.

**Part 5 — The playbook** turns assessment into action: the five-step migration sequence, the modularisation question (short answer: no), the case for JDK 25 as the target, and the argument for making migration a cadence rather than a project.

The appendices carry the reference material: the one-page 38-item table (Appendix A), the removed Java EE modules with Maven coordinates (B), the `sun.misc.Unsafe` eviction timeline (C), and the risk-inventory worksheet (D).

There are three common reading paths:

- *"I'm jumping straight from JDK 8 to 25."* Chapters 0.2 and 0.3, then Part 1 to understand your tools, then all four chapters of Part 2 in order, dipping into Part 3 as each map entry applies to you.
- *"I'm on JDK 17 going to JDK 21 or 25."* Read Chapters 2.3 and 2.4. Cross-reference into Part 3 for anything that applies to your codebase.
- *"I've hit a specific error and I need to fix it."* Go straight to Part 3. Each chapter opens with the exact error message or symptom so you can confirm you're in the right place within seconds.

## Two things you need to understand before you start

### The recompilation paradox

Migration failures don't all behave the same way, and this has real consequences for how you test.

Some code works perfectly as a JDK 8 binary running on JDK 25, but fails the moment you recompile it against the new compiler. The underscore-as-identifier trap is the classic example: your old `.class` files run happily on JDK 25, but `javac` refuses to compile `int _ = 10;` on JDK 9 or later.

The reverse also happens. String concatenation is compiled differently on JDK 9 and later — JDK 8 binaries use `StringBuilder` chains, while recompiled code uses `invokedynamic`. Same source, different bytecode. The JDK 25 version is faster and generates less garbage, and observable behaviour — including the order side-effecting `toString()` calls run in — is identical: the language specification pins evaluation order regardless of how the compiler emits the concatenation. What changes is the bytecode shape, which matters to bytecode-manipulation tooling and to anyone reading `javap` output, not to the program's results.

The practical consequence: you need two test phases, not one. Run your existing JDK 8 binaries on the target JDK first. Then recompile and test again. These are different failure sets. Skip either phase and you will miss things.

### The dependency problem

Your application is roughly 10% your code and 90% someone else's. That ratio is the source of most migration pain.

The errors that surface during a JDK migration are often not in code you wrote. They're in frameworks and libraries that call `setAccessible(true)` on JDK internals, that reference Java EE packages now removed from the platform, that cache `sun.misc.Unsafe` field offsets that are no longer valid, or that were compiled against an ASM version that doesn't understand JDK 25 class files. `jdeps` points at the library. The fix requires either upgrading the library or replacing it — and some of those libraries haven't had a release in years.

This is why the supply chain question is inseparable from the technical migration question. Understanding which of your dependencies are actively maintained is as important as understanding which are technically incompatible. Part 4 covers this in full.

## What this guide does not cover

This guide covers the migration from JDK 8 to JDK 25. It does not cover:

- Green-field development on JDK 25
- GraalVM native image compilation
- Project Loom and virtual thread architecture in depth (virtual threads are relevant to migration in one specific way — thread pinning in dependencies — and that is covered in Chapter 2.3)
- Jakarta EE server migrations (WebLogic, WebSphere, JBoss) beyond the package name changes that affect application code
- Any JDK release after 25

For each failure category, this guide covers the fix for JDK 25. Where a workaround flag exists, it is documented alongside the fix — but every workaround flag in this guide is temporary. Document and track every instance. A project with forty `--add-opens` flags has not migrated; it has deferred.
