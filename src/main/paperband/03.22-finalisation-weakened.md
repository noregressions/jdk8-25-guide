This chapter's worked example contains no failure at all on default settings — and that is the trap:

```
JDK 8:                                 finalized = true
JDK 25 (default):                      finalized = true
JDK 25 with --finalization=disabled:   finalized = false
```

`finalize()` works identically on JDK 25 today. Code relying on it passes every test. What changed is its status: deprecated since JDK 9, terminally deprecated in JDK 18 (JEP 421) — the deck-era habit of citing "forRemoval since 9" is wrong by nine releases — and equipped, since 18, with a launcher flag that turns it off completely. That switch is the fact that matters: the platform has already built and shipped finalisation's absence, and any `finalize()`-dependent cleanup path stops running, silently, wherever that flag — or the removal JEP 421 commits to — lands.

Even before that day, finalisation was always the weakest cleanup contract in the platform: it runs on a GC-triggered background thread, on no schedule, possibly never. "Resources cleaned up at unpredictable times" is not a migration regression — it is the mechanism's specification, and modern JVMs' different GC behaviour (Chapter 3.19) reshuffles the timing you may have accidentally tuned to.

---

## What happened

JEP 421 terminally deprecated finalisation and shipped `--finalization=disabled` so teams can rehearse its absence today. One syntax point that this guide's own history proves is worth stating twice: it is a **launcher option, double-dash, no `-D`**. The system-property spelling `-Dfinalization=disabled` parses fine, does nothing, and gives you false confidence — the verified runs below include it as a control precisely because an earlier version of this project's reference material got it wrong.

The habitats: JDBC-adjacent resource wrappers, native-memory holders, file-handle guards — 2000s-era defensive code, very often in dependencies. Many are *backup* finalisers behind a proper `close()`, which is why disabling finalisation surfaces them as leaks only under load: they were quietly catching the call sites that forgot to close.

## Detect

```bash
grep -rEn "protected void finalize\(\)|@Override\s*protected void finalize" src/
jdeprscan --for-removal --class-path 'libs/*' app.jar     # reports finalize() overrides (forRemoval=true since 18)
```

Then the definitive test — run the suite and a load test with finalisation off:

```bash
java --finalization=disabled -jar app.jar
```

Watch for file-descriptor exhaustion, native-memory growth, and connection-pool starvation. Whatever leaks under that flag is your real dependency on finalisation, found deliberately and on your schedule.

---

## Fix

Two replacements, chosen per resource:

- **`try-with-resources`** wherever the lifetime is scoped — deterministic, immediate, and the right answer for the overwhelming majority of cases.
- **`java.lang.ref.Cleaner`** for the residue: resources whose lifetime genuinely can't be lexically scoped. A `Cleaner` is a deliberate, registered backstop rather than an inherited afterthought — but it shares finalisation's timing weakness, so treat it as insurance, not as the cleanup path.

Delete the `finalize()` overrides as you go; each one left behind re-arms the trap.

## Worked example

From [`examples/22-finalization-weakened`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/22-finalization-weakened), verified on Temurin 8u502 and Temurin 25.0.4 — four runs of a class whose `finalize()` sets a flag:

```
JDK 8:
  finalized = true

JDK 25 (default — finalisation still enabled, still works):
  finalized = true

JDK 25 with --finalization=disabled (the real flag):
  finalized = false

JDK 25 with -Dfinalization=disabled (wrong spelling, as a control — no effect):
  finalized = true
```

The test deliberately does *not* assert on finalisation timing — a pass/fail check on GC scheduling would be flakiness masquerading as rigour. What it proves is sharper: the mechanism your legacy cleanup depends on has a shipped, documented off switch, and the difference between the working and broken world is one launcher flag.
