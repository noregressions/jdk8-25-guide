The first failure a JDK 8 configuration meets on JDK 25 is often not in the code at all. It is this, printed to stderr before a single class loads:

```
Unrecognized VM option 'UseConcMarkSweepGC'
Error: Could not create the Java Virtual Machine.
Error: A fatal exception has occurred. Program will exit.
```

Nothing else in this guide matters until the JVM launches. That is why this category comes first.

---

## What happened

The Concurrent Mark Sweep collector was a mainstream tuning choice for latency-sensitive JDK 8 applications, and `-XX:+UseConcMarkSweepGC` sits in countless startup scripts as a deliberate, once-correct decision. CMS was deprecated in JDK 9 (JEP 291), made obsolete in JDK 14 when the implementation was removed (JEP 363), and the flag itself expired in JDK 15. From that point on the JVM does not warn about it — it refuses to start.

The PermGen sizing flags travelled a different road to the same destination. PermGen was removed in JDK 8 itself, so `-XX:MaxPermSize` and `-XX:PermSize` have been ignored-with-a-warning for the entire JDK 8 era — which is precisely why they survive in so many configurations: they never hurt anyone. On modern JDKs they are rejected outright.

Two things make this category more dangerous than it looks. First, **unrecognised `-XX:` flags are fatal regardless of value** — `-XX:-UseConcMarkSweepGC` (explicitly *disabling* CMS) kills startup just as thoroughly as enabling it, because the JVM no longer knows the flag's name at all. Second, the failure produces no application log, no stack trace, and nothing in your APM tooling — the process exits before any of that machinery exists. If your orchestrator restarts crashed pods automatically, the visible symptom is a crash loop with an empty application log.

---

## Detect

Run the flag audit from Chapter 1.5 before anything else: capture `-XX:+PrintFlagsFinal` output from both JDKs, diff, and check every `<`-prefixed line against your startup configuration. Then grep the places flags actually live — startup scripts, Docker `ENTRYPOINT` lines, Kubernetes manifests, Surefire `argLine`, `JAVA_OPTS`-style environment variables, and IDE run configurations:

```bash
grep -rE "UseConcMarkSweepGC|CMSIncrementalMode|UseParNewGC|MaxPermSize|PermSize" \
  deploy/ docker/ .github/ pom.xml
```

Trial-run the result: `java -version` with your full production flag set, on the target JDK, costs nothing and answers the question definitively.

---

## Fix

Remove the CMS and PermGen flags from every launch path. G1 is the default collector on JDK 25 and is the right starting point for most workloads previously tuned for CMS; ZGC is the option when sub-millisecond pauses matter. Replace `-XX:MaxPermSize` with `-XX:MaxMetaspaceSize` only if you genuinely need to bound metaspace — the default is unbounded, and most PermGen sizing was working around a problem metaspace no longer has.

Do not port CMS tuning parameters (`CMSInitiatingOccupancyFraction` and friends) to G1 equivalents one-for-one. The honest fix is to delete the old tuning wholesale and re-profile under the new collector — Chapter 3.19 covers why JDK 8 performance baselines don't carry over.

## Worked example

From [`examples/01-obsolete-gc-flags`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/01-obsolete-gc-flags), verified 2026-08-07 on Temurin 8u502 and Temurin 25.0.4:

```
$ java8 -XX:+UseConcMarkSweepGC -version
openjdk version "1.8.0_502"
OpenJDK Runtime Environment (Temurin)(build 1.8.0_502-b07)
OpenJDK 64-Bit Server VM (Temurin)(build 25.502-b07, mixed mode)
exit code: 0

$ java25 -XX:+UseConcMarkSweepGC -version
Unrecognized VM option 'UseConcMarkSweepGC'
Error: Could not create the Java Virtual Machine.
Error: A fatal exception has occurred. Program will exit.
exit code: 1
```

The same flag, a supported collector on one JDK and a startup-fatal unknown on the other. The runnable test script is in the repository and takes seconds to point at your own candidate JDK.
