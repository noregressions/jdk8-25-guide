The static tools in the previous chapters analyse what your bytecode *declares*. JDK Flight Recorder (JFR) and `jcmd` observe what your application *does*. That distinction matters because some of the most consequential migration failures are invisible to static analysis: reflective access to internal APIs, frameworks that catch and swallow exceptions, GC behaviour that changes without any error, and resource management paths that only activate under load.

JFR has been production-safe since it was open-sourced in JDK 11. It runs with modest overhead — around 1–2% with default settings — and can be left on in production. The `profile` configuration costs more; use it for short windows, not always-on recording. For migration work, the technique is straightforward: record a baseline on your current JDK, record the same workload on the target JDK, compare the recordings. The differences tell you what changed.

---

## What JFR finds

JFR captures a continuous stream of events from the JVM. The event types most relevant to migration work:

| Event type | What it reveals |
|---|---|
| `jdk.JavaExceptionThrow` | Exception throws (disabled in the default profile — enable it for migration runs) |
| `jdk.ClassLoad` | Every class loaded at runtime — reveals missing classes before they surface as errors |
| `jdk.GCHeapSummary` | GC pause times, heap occupancy, collection counts |
| `jdk.GarbageCollection` | Full GC event details including cause and duration |
| `jdk.ThreadPark` | Thread blocking — useful for identifying virtual thread pinning |
| `jdk.NativeMethodSample` | Native method execution in the call stack |
| `jdk.ObjectAllocationInNewTLAB` | Allocation rate changes between JDK versions |

## What JFR misses

JFR records events that occur during the recording window. Code paths not exercised during your test run produce no events. This is why running JFR during integration tests — not unit tests — is essential. Unit tests exercise individual units in isolation; the failure modes that matter for migration live in the integration points.

JFR also does not interpret events. It tells you that an `InaccessibleObjectException` was thrown at 14:23:07.441. Working out what triggered it and what swallowed it requires navigating the stack trace in JDK Mission Control.

## Starting a recording

**During a test run:**

```bash
java \
  -XX:StartFlightRecording=duration=120s,filename=migration-test.jfr \
  -jar myapp.jar
```

**Attaching to a running JVM** (useful if you can't modify the startup command):

```bash
# Find the process ID
jcmd

# Start a recording
jcmd <pid> JFR.start duration=120s filename=migration-test.jfr

# Check recording status
jcmd <pid> JFR.check

# Dump before duration expires if needed
jcmd <pid> JFR.dump filename=migration-test.jfr
```

**For continuous profiling without a fixed duration:**

```bash
java \
  -XX:StartFlightRecording=name=migration,settings=profile \
  -jar myapp.jar
```

Then dump on demand with `jcmd <pid> JFR.dump name=migration filename=snapshot.jfr`. Note that `settings=profile` collects more events at a higher overhead than the default configuration — keep it for short diagnostic windows rather than always-on recording.

## The baseline comparison technique

Produce two recordings of the same workload:

```bash
# On your current JDK
java8 -XX:StartFlightRecording=duration=60s,filename=baseline-jdk8.jfr -jar myapp.jar

# On JDK 25
java25 -XX:StartFlightRecording=duration=60s,filename=baseline-jdk25.jfr -jar myapp.jar
```

Open both in JDK Mission Control (JMC) and compare:

**GC behaviour** — expect differences. The default GC changed from Parallel to G1 in JDK 9. G1 produces many small pauses rather than fewer large ones. If your application had GC pause SLAs tuned against Parallel GC on JDK 8, those baselines are meaningless on JDK 25 and need to be re-established.

**Exception frequency** — look for new exception types in the JDK 25 recording that don't appear in the JDK 8 baseline. `InaccessibleObjectException`, `UnsupportedOperationException` from degraded Security Manager and thread-lifecycle methods, and `NoClassDefFoundError` for removed packages are the ones to filter for. Any framework that catches these and falls back silently will show as exceptions in JFR even though no stack trace appears in your logs.

**Class loading** — compare the `jdk.ClassLoad` events between the two recordings (or run with `-Xlog:class+load=info`): a class that fails to load on JDK 25 shows up as a gap in the class-load events before any application-level error surfaces, and the exception it triggers is visible via `jdk.JavaExceptionThrow` (disabled in the default profile) or `-Xlog:exceptions=info`. This catches conditional class loading patterns that `jdeps` cannot see.

**Allocation rates** — recompiled code often has different allocation profiles. String concatenation via `invokedynamic` produces less garbage than `StringBuilder` chains. Nestmate access removes synthetic wrapper objects. The allocation rate going *down* after migration is expected and welcome.

## Using jcmd for live JVM inspection

`jcmd` sends diagnostic commands to a running JVM. During migration testing, three commands are particularly useful:

```bash
# Full JVM information — version, flags, classpath, system properties
jcmd <pid> VM.info

# All active JVM flags with their current values
jcmd <pid> VM.flags

# Heap summary — GC algorithm, heap sizes, generation details
jcmd <pid> GC.heap_info
```

`VM.flags` is the runtime equivalent of the static `PrintFlagsFinal` audit in Chapter 1.5. It shows you the flags actually in effect, including any that were set programmatically or adjusted by ergonomics rather than on the command line.

## JDK Mission Control

JFR recordings are binary files. JDK Mission Control (JMC) is the desktop tool for analysing them — it visualises events on a timeline, lets you filter by event type, and shows stack traces for individual events.

JMC is available as a standalone download from `openjdk.org/projects/jmc`. Open both your JDK 8 baseline and JDK 25 recording, put them side by side, and use the Automated Analysis tab first — it flags anomalies automatically and is a faster starting point than manual event browsing.
