```
Error occurred during initialization of boot layer
java.lang.LayerInstantiationException: Package com.example in both module modA and module modB
```

A "split package" is one package whose classes live in more than one JAR. On the classpath this has always been legal, common, and mostly harmless — the first class found wins, and a decade of applications shipped this way without anyone noticing. The module system forbids it outright: every package must belong to exactly one module, and the JVM enforces that at boot-layer construction, before any application code runs.

---

## What happened

This category has a property most of Part 3 doesn't: **nothing breaks unless you opt in.** The classpath remains fully supported on JDK 25, with its JDK 8 semantics intact — the unnamed module swallows all classpath JARs and split packages inside it are tolerated exactly as before. The failure appears only when JARs move to `--module-path`, where each JAR becomes an automatic or explicit module and the one-package-one-module rule bites.

Which is why the practical risk is concentrated at a specific moment: the team that decides, mid-migration, to adopt modules — usually because `jlink` needs them for a custom runtime image — and discovers that JARs which coexisted peacefully for years cannot occupy the same module graph. Old multi-artefact libraries are the classic source: pre-modular versions of common APIs, `*-api` and `*-impl` pairs sharing a package, or two vendors both shipping `javax.something` shims.

The failure is at least immediate and explicit: it names the package and both offending modules, at startup, every time. There is no intermittent version of this problem.

---

## Detect

```bash
jdeps -s --module-path libs/ app.jar        # reports overlapping packages
```

Or simply trial-run your application with the JARs on the module path — the boot layer either constructs or it doesn't, and the error names the first collision. Repeat, because it reports one collision at a time.

---

## Fix

In order of preference:

1. **Stay on the classpath.** If nothing in your migration actually requires modules — and Chapter 5.2 argues most migrations don't — this category costs you nothing. Migrating JDK versions and adopting the module system are separate decisions.
2. **Upgrade the offending libraries.** Most actively-maintained libraries reorganised their packages for module compatibility years ago; splits usually indicate a pre-2018 version.
3. **Merge or shade.** Where the split is genuinely yours (or the library is dead), combine the JARs into one module, or relocate packages with the Maven Shade plugin.

## Worked example

From [`examples/11-split-packages-module-path`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/11-split-packages-module-path), verified on Temurin 25.0.4. Unusually for this catalogue there is no JDK 8 side — the module path doesn't exist there. Instead the test runs the identical split-package setup (`com.example` defined in both `modA` and `modB`) twice on JDK 25:

```
JDK 25, classpath (package split across two JARs — the JDK 8 behaviour):
  openjdk version "25.0.4" 2026-07-21 LTS
  exit=0

JDK 25, module path (same two packages, same classes):
  Error occurred during initialization of boot layer
  java.lang.LayerInstantiationException: Package com.example in both module modA and module modB
  exit=1
```

Same JARs, same JDK — the only variable is which flag put them on which path. That is the whole category in two runs.
