```
MainDirect.java:9: error: cannot find symbol
    p.setName("Ada");
     ^
  symbol:   method setName(String)
```

Lombok generates getters, setters, builders, and more at compile time, via an annotation processor that — for most of its life — `javac` discovered automatically from the classpath. From JDK 23, `javac` no longer runs annotation processors unless explicitly told to (JDK-8321319; there is no JEP for it). Builds that relied on implicit discovery stop generating the methods, and what happens next depends entirely on who calls them.

---

## What happened

Two failure shapes, both verified with real Lombok jars rather than simulation, and the distinction matters because the folklore only describes one of them:

**Direct callers fail loudly, at compile time.** `p.setName(...)` in ordinary code is a symbol reference; when generation doesn't run, compilation fails with "cannot find symbol". Visible, immediate, diagnosable — a *harder and better* failure than the legend suggests.

**Reflective and framework-style callers fail silently-then-late.** `Class.getMethod("setName", ...)` compiles against nothing; the build genuinely succeeds, and the absence surfaces at runtime as `NoSuchMethodException` — in production, wearing a framework stack trace. This is the "build succeeds silently" scenario, and it is real, but it specifically requires a reflective caller: web frameworks binding request parameters, serialisation libraries, mappers. Which describes... most of the places Lombok-generated accessors get called in a typical service.

Two separate requirements hide under the one fix, and satisfying only one still fails:

1. **Explicit processor configuration** — the answer to the JDK 23 discovery change.
2. **A Lombok version that supports JDK 25 class files** — the floor is **1.18.40** (changelog-verified: "JDK25 support added", September 2025); recommend **1.18.44+** in practice, as 1.18.42 and 1.18.44 fix JDK 25 bugs on top. A JDK-8-era pin like 1.18.20 fails on 25 no matter how correctly the processor is wired.

## Detect

```bash
mvn dependency:tree | grep lombok                      # version check
grep -A5 "maven-compiler-plugin" pom.xml | grep -c annotationProcessorPaths
```

If the version is below 1.18.40 or the processor path isn't explicit, the build is trading on defaults that no longer hold. The empirical check: trial-compile on the target JDK — direct callers make this category self-announcing, and a codebase with *only* reflective callers is exactly the one that must not skip the trial run's test suite.

---

## Fix

Explicit configuration, current version — both:

```xml
<plugin>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <annotationProcessorPaths>
      <path>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <version>1.18.44</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>
```

(Gradle: `annotationProcessor 'org.projectlombok:lombok:1.18.44'` alongside `compileOnly`.) The same explicit-paths treatment applies to every other processor in the build — MapStruct, Immutables, Dagger — Lombok is merely the most common casualty. Chapter 1.9 covers the OpenRewrite side of this cleanup.

## Worked example

From [`examples/29-lombok-annotation-processor-trap`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/29-lombok-annotation-processor-trap), verified on Temurin 8u502 and Temurin 25.0.4 with real Lombok jars fetched from Maven Central. `Person.java` uses `@Getter @Setter`; two callers:

```
1. JDK 8, Lombok 1.18.30, no explicit -processorpath:
  compile exit=0, run exit=0: Ada 30                    <- the old implicit-discovery world

2. JDK 25, no explicit -processorpath, DIRECT caller:
  MainDirect.java:9: error: cannot find symbol
      p.setName("Ada");
  compile exit=1                                        <- fails loudly, at compile time

3. JDK 25, no explicit -processorpath, REFLECTIVE caller:
  compile exit=0  ("the build succeeds")
  Exception in thread "main" java.lang.NoSuchMethodException: Person.setName(java.lang.String)
  run exit=1                                            <- fails silently, at runtime

4. JDK 25, WITH explicit -processorpath:
  compile exit=0, run exit=0: Ada 30                    <- the fix
```

Runs 2 and 3 are the same missing configuration expressed through two callers — one build error, one production incident.
