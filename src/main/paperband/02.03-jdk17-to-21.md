On paper 17→21 looks gentle — no module system, no mass package removal. In practice it is the span where the *silent* changes concentrate: the default charset, the Security Manager's default, finalisation's terminal notice, and the thread-lifecycle methods finally growing teeth.

| Change | Level | Chapter |
|---|---|---|
| **UTF-8 becomes the default charset everywhere (18, JEP 400)** | Runs But Wrong | 3.18 |
| **`java.security.manager` defaults to `disallow` (18, per JEP 411)** | Crash | 3.8 |
| Finalisation deprecated for removal; `--finalization=disabled` ships (18, JEP 421) | Runs But Wrong | 3.22 |
| `Thread.stop` terminally deprecated (18) | — announcement | 3.10 |
| Biased locking implementation removed (18); flag expired (19) | Won't Start / RBW | 3.24 |
| `ThreadGroup` stop/suspend/resume degraded to throw (19–20) | Crash | 3.21 |
| **`Thread.stop()`/`suspend()`/`resume()` throw (20)** | Crash | 3.10 |
| `this-escape` lint arrives (21) — `-Werror` builds feel it | Recompile | 3.30 |
| Virtual threads final (21, JEP 444) | — see note | — |

The JDK 18 row pair deserves emphasis because it is so widely misdated: `setSecurityManager()` throwing "since JDK 24" is folklore — the default flipped at **18**, with `-Djava.security.manager=allow` as the opt-out through 23. Teams on 18–21 who set `=allow` have deferred the failure, not escaped it (3.8).

**A note on virtual threads.** JEP 444 (21) is the span's headline feature but mostly out of this guide's scope — with one migration-relevant edge: virtual threads *pin* on code that blocks inside `synchronized` blocks, which JDK-8-era libraries do heavily. If adopting virtual threads is part of your migration's motivation, treat "pinning in dependencies" as one more reason the dependency-currency work of Part 4 comes first. (JDK 24's JEP 491 later removed most pinning — one more argument for 25 as the target rather than 21.)

**If this is your hop:** budget for comparison testing over crash-hunting — 3.18 and the other silent changes don't announce themselves. Run the two-JDK output-diff discipline of Chapter 1.6 on anything that formats, encodes, or stores data. And use the span's gift: `--finalization=disabled` and the JDK 18+ charset flags let you rehearse those end-states on today's JDK, deliberately.

Tools for this span: baseline comparison (1.6) is the workhorse; `jdeprscan` (1.2) tracks the terminal deprecations; the runtime flag kit (1.7) provides the rehearsal switches.
