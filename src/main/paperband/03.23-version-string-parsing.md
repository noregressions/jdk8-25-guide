```
JDK 8:   java.version = 1.8.0_502    startsWith("1.") = true
JDK 25:  java.version = 25.0.4       startsWith("1.") = false
```

For Java's first two decades, `java.version` began with `1.` — `1.4.2`, `1.6.0_45`, `1.8.0_292`. An entire folk tradition of version detection grew on that shape: `startsWith("1.")` to mean "old Java", `substring(2, 3)` to extract the "real" major version, splitting on `_` for the update number. JEP 223 (JDK 9) replaced the scheme with the sane one — `9`, `11.0.19`, `25.0.4` — and every one of those parsers quietly started lying.

---

## What happened

No parser throws on the new strings; they all *return something*. `startsWith("1.")` returns false; `substring(2, 3)` of `25.0.4` returns `.`; a split-on-first-dot "major version" returns 25 where the old-scheme code expected 8 to appear as `1`. The code runs to completion and the application takes a branch — just not the one its author reasoned about.

The realistic damage pattern deserves spelling out:

```java
if (System.getProperty("java.version").startsWith("1.")) {
    // the Java 8 path — every line exercised daily for years
} else {
    // the "Java 9+" path — quite possibly never executed since it was written
}
```

On JDK 25 the *else* branch runs: code that has been dead for a decade, untested, unreviewed, and now in charge. The failure that follows won't mention versions at all — it will look like whatever that stale branch does wrong. Library code is the usual carrier: compatibility shims in older frameworks did exactly this to choose between reflection strategies.

---

## Detect

```bash
grep -rEn "java\.version|java\.specification\.version|startsWith\(\"1\.\"" src/
```

Review every hit's parsing assumptions against both string shapes. `java.specification.version` deserves inclusion: it moved from `1.8` to `9`, `11`, `25` on the same schedule, and code comparing it numerically after stripping a `1.` prefix has the same disease.

---

## Fix

`Runtime.version()`, available since JDK 9, returns a structured `Runtime.Version` — `feature()` gives the major version as an int, and comparisons come for free:

```java
if (Runtime.version().feature() >= 17) { ... }
```

One migration-period wrinkle, demonstrated in the worked example: `Runtime.version()` doesn't exist on JDK 8, so code that must still *run* on 8 during the transition can't simply switch to it. The bridge pattern is to parse defensively — treat a leading `1.` as old-scheme, otherwise take digits up to the first dot — in one shared utility rather than at every call site, and delete it the day JDK 8 support ends. (Build-side, `javac --release 8` will refuse the new API anyway, which at least makes the constraint visible.)

---

## Worked example

From [`examples/23-version-string-parsing`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/23-version-string-parsing), verified on Temurin 8u502 and Temurin 25.0.4 — identical naive parsing on both JDKs, then the fix attempted on 8:

```
JDK 8, naive java.version parsing:
  java.version = 1.8.0_502
  naive check startsWith("1.") = true
  naive major-version extraction (split on first dot) = 1

JDK 25, naive java.version parsing (identical code):
  java.version = 25.0.4
  naive check startsWith("1.") = false
  naive major-version extraction (split on first dot) = 25

Attempting to compile the modern fix (Runtime.version()) under JDK 8:
  VerModern.java:8: error: cannot find symbol
          System.out.println("Runtime.version() = " + Runtime.version());
  exit=1
```

Note the naive "major version" column: `1` on one JDK, `25` on the other — the same code producing numbers from two different numbering systems, with no error to flag the discontinuity.
