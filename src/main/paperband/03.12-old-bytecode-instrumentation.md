```
java.lang.IllegalArgumentException: Unsupported class file major version 69
```

If that message appears in a stack trace running through Spring, Hibernate, Mockito, JaCoCo, or anything else that generates proxies or instruments classes, the cause is always the same: somewhere in the dependency tree, a bytecode-reading library is older than the class files it has been asked to parse.

---

## What happened

Every class file declares a major version — 52 for JDK 8, 61 for 17, 65 for 21, 69 for 25 (Chapter 1.4 has the full table). Bytecode libraries like ASM and ByteBuddy validate that number and refuse versions newer than they know, because parsing an unknown format blind would be worse. The result is a treadmill: each JDK release invalidates every ASM pinned before that release existed.

What makes this category persistent rather than a one-off fix is *where* ASM lives. Almost nothing depends on it directly — it arrives shaded or transitively inside proxy generators, mocking frameworks, coverage tools, AOP weavers, and application servers. Your `pom.xml` says Mockito 3.x; three levels down, that means an ASM that has never heard of version 69. The failure then surfaces at runtime, wearing the outer framework's stack trace, often only on the code path that first triggers proxy generation.

The version floors for a JDK 25 target: **ASM 9.8+**, **ByteBuddy 1.17.5+**, **Mockito 5.x** — treating each as "at least", and verifying against the library's own release notes for your exact combination, since these floors move with every JDK release. The same mechanism breaks build-time tooling (JaCoCo, older Gradle, Kotlin/Scala compilers); that build-side variant is Chapter 3.35's subject.

---

## Detect

```bash
mvn dependency:tree | grep -iE "asm|bytebuddy|byte-buddy|cglib|javassist"
```

Then check each hit's version against its JDK 25 support floor. For shaded copies — which `dependency:tree` can't see — the reliable detector is empirical: run the test suite on the target JDK and grep for "Unsupported class file major version". A clean tree plus a failing run means a shaded or vendored copy somewhere.

---

## Fix

Upgrade the *outer* dependency, not the inner one: bumping ASM directly rarely helps when the consuming framework shades or pins it. Mockito, Spring, Hibernate, and the coverage tools all publish JDK-compatibility matrices — this is exactly the toolchain-first upgrade step the playbook (Chapter 5.1) puts before the JDK switch itself.

One deferral worth knowing: compiling with `javac --release 8` on JDK 25 emits version-52 class files, which old instrumentation can still read. That keeps a stuck tool alive through a transition — but it defers the problem, and costs you 17 releases of language features. It is a bridge, not a destination.

## Worked example

From [`examples/12-old-bytecode-instrumentation`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/12-old-bytecode-instrumentation), verified on Temurin 8u502 and Temurin 25.0.4. No library is vendored into the test harness, so it demonstrates the underlying mechanism directly: compile the same trivial class under both JDKs, confirm the version really moved (52 → 69), then feed the newer class file to the older reader — in this case JDK 8's own class loader, which takes exactly the code path an old ASM takes internally:

```
JDK 8  compiled class file major version: 52
JDK 25 compiled class file major version: 69

Loading the JDK-25-compiled class file with JDK 8's JVM:
  Exception in thread "main" java.lang.UnsupportedClassVersionError: Simple has
  been compiled by a more recent version of the Java Runtime (class file version
  69.0), this version of the Java Runtime only recognizes class file versions up
  to 52.0
  exit=1
```

The JVM's version of the message is refreshingly explicit. Library wrappers are terser — but the trigger condition is identical: a reader older than what it's reading.
