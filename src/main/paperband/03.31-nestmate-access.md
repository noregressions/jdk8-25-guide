| | |
|---|---|
| **Level** | Recompilation Surprises |
| **Introduced** | JDK 11 (JEP 181 — Nest-Based Access Control) |
| **Symptom** | None, behaviourally. Recompiled inner-class access swaps `access$000` bridge methods for `NestHost`/`NestMembers` attributes |
| **Detect** | `javap -c -v` — look for `NestHost`/`NestMembers`, and for the absence of `access$` methods |

```
javac8-compiled Outer.class:  access$ bridge methods=1, NestHost/NestMembers attrs=0, size=853B
javac25-compiled Outer.class: access$ bridge methods=0, NestHost/NestMembers attrs=2, size=1023B
```

Every level of this catalogue deserves one entry that improves on recompile, and this is it. Since Java 1.1, an outer class touching its inner class's private members forced `javac` to fake the access with synthetic package-private bridge methods — the `access$000` frames that have photobombed stack traces for twenty-five years. JEP 181 (JDK 11) taught the JVM about *nests* natively: classes compiled as a nest declare each other via `NestHost`/`NestMembers` attributes, and private access between nestmates just works, no bridges required.

---

## What happened

On recompile with a modern `javac`, the bridge methods vanish and the nest attributes appear. Behaviour is identical — the verified example reads the same private field, gets the same answer, both ways. What improves: stack traces and debugger step-through lose their synthetic frames; profilers stop attributing time to methods no human wrote; and bytecode tooling (Chapter 3.12's clientele) has fewer synthetic members to model.

Two second-order effects earn the chapter its place in a *migration* guide:

**The serialisation coupling.** Those disappearing synthetic methods feed the computed `serialVersionUID` hash — this is precisely the mechanism behind Chapter 3.25's drift. The one that helps triggers the one that hurts, which is the neatest argument in the book for explicit UIDs.

**The size claim that measurement reversed.** Migration folklore (and earlier versions of this project's material) lists "smaller class files" among the benefits. For the verified test class, the file got **bigger** — 853 to 1023 bytes — because the `NestHost`/`NestMembers` attributes and their constant-pool entries carry overhead that removing a single bridge method doesn't offset. Large classes with many cross-nest accesses can net out smaller; tiny ones don't. The honest claim is "different class shape, cleaner semantics", not a size promise — a small specimen of this guide's general rule that plausible mechanisms still need measuring.

---

## Detect

Nothing needs detecting for safety. For the curious, or for tooling triage:

```bash
javap -v Outer.class | grep -E "NestHost|NestMembers|access\$"
```

tells you which era compiled any given class file.

---

## Fix

None needed — this is the free improvement. The action items live next door: pin `serialVersionUID` before the recompile changes the hash (Chapter 3.25), and confirm bytecode-reading tools are on versions that understand nest attributes (Chapter 3.12 — anything ASM 7+ era does).

## Worked example

From [`examples/31-nestmate-access`](https://github.com/noregressions/jdk8-25-guide/tree/main/examples/31-nestmate-access), verified on Temurin 8u502 and Temurin 25.0.4. `Outer`'s private field is read from a nested static class:

```
Behaviour, JDK 8:
  secret via Inner = 42
Behaviour, JDK 25:
  secret via Inner = 42

javac8-compiled Outer.class:  access$ bridge methods=1, NestHost/NestMembers attrs=0, size=853B
javac25-compiled Outer.class: access$ bridge methods=0, NestHost/NestMembers attrs=2, size=1023B
```

Identical answers, different machinery — and a 20% size *increase* on the class everyone's slide deck says gets smaller.
